## 1. 모듈 개요

### 모듈 목표

이 모듈을 마치면 다음을 수행할 수 있습니다.

- 기존 아키텍처의 당면 과제 설명

## 2. 모던 애플리케이션

### 2.1 모던 애플리케이션의 세 축

AWS의 모던 애플리케이션 정의는 다음과 같습니다.

> AWS는 모던 애플리케이션을 모던 기술, 아키텍처, 소프트웨어 전달 관행 및 운영 프로세스의 조합을 바탕으로 개발된 클라우드 네이티브 애플리케이션으로 정의합니다. 모던 애플리케이션은 마이크로서비스 아키텍처 패턴, 서버리스 운영 모델, 자동화된 소프트웨어 전달 프로세스를 통해 구축됩니다.

세 축을 표로 정리하면 이렇습니다. 이 모듈은 첫 두 축을 다루고, 세 번째 축의 개발 민첩성과 관찰 기능은 다른 모듈에서 다룹니다.

| 축 | 내용 | 이 문서 |
|---|---|---|
| 아키텍처 패턴 | 마이크로서비스 (완전히 독립적) | [3장](#3-모놀리스에서-마이크로서비스로) |
| 운영 모델 | 서버리스 | [4장](#4-서버리스-운영-모델) |
| 소프트웨어 전송 | DevOps — 계획 → 코드 → 구축 → 테스트 → 릴리스 → 배포 → 운영 → 모니터링 | [3.9절](#39-소프트웨어-전달-devops) |

### 2.2 모던 애플리케이션이 목표로 하는 네 가지

모던 애플리케이션이 목표로 하는 네 가지 특성입니다.

| 특성 | 내용 |
|---|---|
| 속도 | 고객과 시장의 필요에 맞게 빠르게 업데이트할 수 있습니다 |
| 확장성 | 수백만 명의 사용자에 맞게 빠르게 크기를 확장하여 수 페타바이트 데이터를 처리하고 전 세계에서 사용할 수 있습니다 |
| 복원력 | 수명 주기 전체와 배포 과정에서 복원력을 발휘합니다. 복원력이 애플리케이션에 기본적으로 적용되기 때문에 애플리케이션이 빠르게 응답하고 장애 발생 후 복구될 수 있습니다 |
| 보안 | 각 서비스를 대상으로 보안이 설정되기 때문에 애플리케이션과 수명 주기 수준에서 보안이 유지됩니다 |

AWS 백서 `Implementing Microservices on AWS`(2023년 7월 31일 발행)도 같은 방향으로 기술합니다. 마이크로서비스는 잘 정의된 API로 통신하고 자율적인 팀이 관리하는 작고 소결합된 서비스에 의존하며, 이점은 확장성·복원력·유연성 향상과 더 빠른 개발 주기입니다. 백서는 마이크로서비스 아키텍처가 애자일 소프트웨어 개발, 서비스 지향 아키텍처, API 우선 설계, CI/CD 같은 여러 분야의 개념을 결합한 것이라고 설명하고, Twelve-Factor App 설계 패턴을 포함하는 경우가 많다고 덧붙입니다.

> — 출처: [Implementing Microservices on AWS](https://docs.aws.amazon.com/whitepapers/latest/microservices-on-aws/microservices-on-aws.html)

### 2.3 마이크로서비스란 무엇인가

모놀리스와 마이크로서비스를 한 줄로 대비하면 이렇습니다.

| 구분 | 요약 |
|---|---|
| 모놀리스 | 모든 기능 수행 |
| 마이크로서비스 | 하나의 기능 수행 / 완전히 독립적 / API |

각각의 정의는 다음과 같습니다.

- **모놀리스 애플리케이션**: 사용자 인터페이스와 데이터가 단일 플랫폼의 단일 프로그램으로 결합되는 밀결합된 서비스입니다. 다른 컴퓨팅 애플리케이션과는 별개의 독자적이고 독립적 애플리케이션입니다.
- **마이크로서비스 애플리케이션 서비스의 특징**: 엄격하고 범위가 지정됨 / 강력하게 캡슐화됨 / 소결합됨 / 독립적으로 배포할 수 있음 / 확장 가능

이 다섯 특징은 백서의 서술과 일치합니다. 백서는 마이크로서비스가 "잘 정의된 API로 통신하고 자율적인 팀이 관리하는 작고 소결합된 서비스"라고 요약하며, 조직 측면에서도 팀이 보통 "투 피자 팀"이라고 불릴 만큼 작고, 생성부터 배포·유지 관리까지 서비스에 대한 전적인 책임을 진다고 기술합니다.

> — 출처: [Implementing Microservices on AWS](https://docs.aws.amazon.com/whitepapers/latest/microservices-on-aws/microservices-on-aws.html)

### 2.4 마이크로서비스가 항상 답은 아니다 🆕

마이크로서비스의 이점만 보면 놓치기 쉬운 단서가 백서에 있습니다. 마이크로서비스가 많은 이점을 제공하지만 **사용 사례별 요구와 비용을 평가해야 하고, 어떤 경우에는 모놀리식 아키텍처나 다른 접근이 더 적절할 수 있으므로 규모·복잡성·구체적 사용 사례를 고려해 사례별로 판단해야 한다**고 기술합니다.

강의에서 이 단서를 함께 말해야 하는 이유는 두 가지입니다.

| 이유 | 내용 |
|---|---|
| 분해 비용이 실재한다 | 마이크로서비스를 생성하거나 기존 모놀리스 애플리케이션을 리팩터링하는 작업은 쉽지 않습니다 |
| 분산 트랜잭션이 어려워진다 | 서비스별 데이터베이스로 나누면 관계형 데이터베이스의 2단계 커밋(2PC)을 쓸 수 없습니다. 보상 트랜잭션을 직접 설계해야 합니다([3.8절](#38-분산-트랜잭션과-사가-오케스트레이션-패턴)) |

> — 출처: [Implementing Microservices on AWS](https://docs.aws.amazon.com/whitepapers/latest/microservices-on-aws/microservices-on-aws.html)

## 3. 모놀리스에서 마이크로서비스로

### 3.1 모놀리스 애플리케이션

모놀리스의 특징 아홉 가지는 다음과 같습니다. 왼쪽이 특징이고 오른쪽은 그것이 개발 현장에서 어떤 문제로 나타나는지에 대한 설명입니다.

| 특징 | 무엇이 문제가 되는가 |
|---|---|
| 모든 기능 수행 | 한 프로그램이 프레젠테이션·로직·데이터를 모두 담습니다 |
| 밀결합된 기능 | 결합 수준이 높으면 종속성도 높아 개발·테스트 복잡성이 증가합니다 |
| 각 런타임 인스턴스 별 상태 존재 | 인스턴스가 상태를 들고 있으면 수평 확장이 어렵습니다 |
| 단일 기술 스택 | 기능마다 더 적합한 언어·런타임을 고를 수 없습니다 |
| 제한적 데이터 옵션 | 하나의 데이터 저장소를 모든 액세스 패턴에 맞춰야 합니다 |
| 기술 계층 중심으로 구성 | 팀이 비즈니스 기능이 아니라 UI·미들웨어·DB 같은 기술 도메인으로 나뉩니다 |
| 배포 복잡성 | 가장 느린 구성 요소의 속도로만 배포할 수 있습니다 |
| 배포 일정의 경직성 | 여러 팀이 하나의 배포 일정에 묶입니다 |
| 운영 오버헤드 | 전체를 함께 운영해야 합니다 |

대표적인 예는 전형적인 3티어 아키텍처이고, 로직 계층에 "노트 처리 · 노트 검색 · 노트 읽기"가 함께 들어 있습니다.

| 계층 | 설명 |
|---|---|
| 프레젠테이션 | HTTP 요청을 관리하고 HTML 또는 JSON/XML(웹 서비스 API)을 이용해 응답합니다 |
| 비즈니스 로직 | 애플리케이션 서버 |
| 데이터 계층 | 데이터베이스 서버에 액세스하는 데이터 액세스 객체가 포함됩니다 |

결론은 이렇습니다. 이 아키텍처는 기능적이긴 하지만, 비즈니스가 빠르게 변하고 성장한다면 원하는 만큼 빠르게 애플리케이션을 시작하거나 업데이트할 수가 없습니다.

### 3.2 마이크로서비스 아키텍처

마이크로서비스의 특징 일곱 가지를 모놀리스 항목과 나란히 놓으면 무엇을 바꾸는 것인지가 분명해집니다.

| 항목 | 모놀리스 | 마이크로서비스 |
|---|---|---|
| 기능 범위 | 모든 기능 수행 | 최소 기능 서비스 |
| 결합 | 밀결합된 기능 | 개별적으로 배포되지만 서로 상호 작용함 |
| 상태 | 각 런타임 인스턴스 별 상태 존재 | 상태정보는 외부에 저장 |
| 기술 선택 | 단일 기술 스택 | 각 마이크로서비스를 대상으로 기술 선택 |
| 데이터 | 제한적 데이터 옵션 | 목적 기반 데이터 옵션에 적합 |
| 구성 기준 | 기술 계층 중심으로 구성 | 비즈니스 기능 중심으로 구성 |
| 운영 | 운영 오버헤드 | 서버리스 및 자동 작동 모델 |

이 표에서 놓치기 쉬운 점이 하나 있습니다.

> 모던 애플리케이션은 데이터, 로직, 프레젠테이션 레이어 계층 같은, 모놀리스 애플리케이션에 있는 것과 동일한 여러 구성 요소로 구성됩니다. 하지만 몇 가지 주요 차이점도 있습니다. 각 마이크로서비스는 다른 마이크로서비스와 확연하게 구분되며, 저마다 고유한 지속성 메커니즘이 있습니다.

즉 계층이 사라지는 것이 아니라, 계층을 가로로 자르는 대신 **비즈니스 기능 단위로 세로로 자르고 각 조각이 자기 데이터 저장소를 갖는다**는 뜻입니다.

"상태정보는 외부에 저장"이라는 특징은 서버리스 컴퓨팅과 직접 맞물립니다. AWS 결정 안내서는 Fargate 컨테이너가 실행 중 메모리 상태를 유지할 수 있는 반면 **Lambda는 설계상 스테이트리스여서 외부 저장소가 필요하다**고 기술합니다.

> — 출처: [AWS Fargate or AWS Lambda](https://docs.aws.amazon.com/decision-guides/latest/decision-guides/fargate-or-lambda.html)

### 3.3 마이크로서비스 아키텍처의 이점

마이크로서비스 아키텍처의 여섯 가지 이점은 다음과 같습니다. 하위 항목을 함께 실었습니다.

| 이점 | 하위 항목 |
|---|---|
| 개발 민첩성 | 코드를 읽을 수 있습니다 / 기술 스택을 쉽게 변경할 수 있습니다 / 소규모 팀 간의 협업이 증가합니다 / 변경 사항이 다른 서비스와는 별개로 적용됩니다 |
| 빠르고 독립적인 배포 | 마이크로서비스는 독립적으로 배포됩니다 / 배포 시간이 더 짧습니다 / 배포 프로세스를 쉽게 자동화할 수 있습니다 |
| 향상된 보안 | 모든 서비스가 안전합니다 |
| 독립적인 크기 조정 | 마이크로서비스는 독립적으로 크기를 조정할 수 있습니다 |
| 가용성 및 복원력 증진 | 장애 격리가 개선되었습니다 |
| 비즈니스 기능에 기반한 구성 | 다른 애플리케이션의 서비스를 재사용할 수 있습니다 |

이 목록의 근거는 한 문장으로 요약됩니다. 마이크로서비스는 작고 독립적인 단위이기 때문에 이런 이점이 있습니다.

### 3.4 서비스 경계와 도메인 주도 설계 🆕

새 개발을 시작하는 방법은 다음과 같습니다.

- 책임감 있는 문화를 조성하여 실험 해보기
- 마이크로서비스를 사용하여 애플리케이션을 개별화 구성 — API를 통해 제대로 정의된 인터페이스 / 각 마이크로서비스는 단일 기능에 맞게 최적화됨 / 각 서비스는 다른 서비스와는 별개임
- 예: 도메인 주도 설계 — 마이크로서비스의 기능은 도메인 컨텍스트 내에 존재 / 다른 도메인과의 통합 지점 정의

도메인 주도 설계는 한 줄 예시에 그치기 쉽지만, AWS Well-Architected 신뢰성 원칙 **REL03-BP02**는 이를 실행 가능한 지침으로 풀어냅니다. 마이크로서비스는 도메인 모델과 **바운디드 컨텍스트(bounded context)** 를 써서 비즈니스 컨텍스트 경계에 맞춰 서비스 경계를 그립니다. 바운디드 컨텍스트는 비즈니스 로직을 격리·캡슐화해 팀이 장애 처리 방법을 더 잘 판단하게 합니다.

문서가 제시하는 안티 패턴은 앞서 본 모놀리스의 "기술 계층 중심으로 구성"과 정확히 겹칩니다.

| 구분 | 내용 |
|---|---|
| 안티 패턴 | UI·미들웨어·데이터베이스 같은 **기술 도메인 중심으로 팀을 구성**하는 것 |
| 안티 패턴 | 애플리케이션이 **여러 도메인 책임에 걸치는** 것 |
| 안티 패턴 | 도메인 엔터티 라이브러리 같은 **도메인 종속성을 서비스 간에 공유**하는 것 |
| 구현 단계 | 이벤트 스토밍 워크숍으로 이벤트·명령·애그리게이트·도메인을 식별 |
| 구현 단계 | 바운디드 컨텍스트로 도메인을 서비스로 나누기 |
| 구현 단계 | 기존 모놀리스에는 버블 컨텍스트나 안티 커럽션 레이어 같은 전술적 기법 적용 |

모놀리스 분해에는 **비즈니스 역량별·서브도메인별·트랜잭션별** 패턴이 도메인 주도 접근과 잘 맞습니다.

> — 출처: [REL03-BP02 Build services focused on specific business domains and functionality](https://docs.aws.amazon.com/wellarchitected/latest/reliability-pillar/rel_service_architecture_business_domains.html)

### 3.5 통합 패턴: API 기반과 이벤트 기반

통합은 두 범주로 나뉩니다.

| 구분 | 처리 방식 | 내용 |
|---|---|---|
| API 기반 | 동기식 | 애플리케이션과 서비스는 API를 통해 연결되고 통신함(AWS 서비스는 서비스 API를 제공함) / HTTP 및 HTTPS 통신 프로토콜 |
| 이벤트 기반 | 비동기식 | 상황이 발생했음을 알리는 메시지(AWS 리소스는 상태 변경 시 이벤트를 생성할 수 있음) / 소비자가 이벤트를 구독 / 공급자가 이벤트를 생성 |

고려 사항 네 가지는 그대로 옮길 가치가 있습니다.

- 모던 애플리케이션은 두 가지 유형의 통합을 모두 사용합니다.
- 서비스 내에서 통신합니까, 서비스 사이에서 통신합니까? 일반적으로 서비스는 API에서 래핑되지만 메시지와 이벤트를 내부적으로 사용합니다.
- 이벤트 기반 통신은 거의 무한대로 확장 가능하며, 0으로 크기를 조절할 수도 있어 비용 상의 이점을 누릴 수 있습니다.
- 이벤트 기반 애플리케이션은 서비스와 서비스를 구축한 팀 간의 디커플링을 활성화합니다. 이러한 디커플링은 팀의 민첩성을 개선합니다.

AWS Serverless Developer Guide는 이벤트 기반 아키텍처(EDA)를 **서버리스 학습 경로의 첫 단계**로 제시하며, 서비스가 이벤트를 통해 상호 작용하는 방식을 이해하는 것이 성공적인 서버리스 개발에 필수라고 기술합니다. 이벤트는 상태의 변화 또는 업데이트를 나타냅니다(장바구니에 담긴 항목, 스토리지에 업로드된 파일, 배송 준비가 된 주문). 이벤트는 수량·가격·통화처럼 상태를 담을 수도 있고 `customerId`·`orderId`처럼 관련 정보를 조회할 식별자만 담을 수도 있습니다.

같은 문서가 요청/응답 주기와 이벤트 기반 구현을 대비하는 방식은 강의에서 쓸 만합니다.

| 구분 | 애플리케이션이 직접 다루는 일 |
|---|---|
| 전통적인 요청/응답 | 인바운드 요청 수락 · 라우팅 · 전역 데이터와 유틸리티 서비스 생성 · 웹 훅 구현 · 요청 처리 · 응답 직렬화 · 메타데이터 추가 · 응답 전송 — 여덟 단계 |
| 이벤트 기반 | API Gateway가 인바운드 URL·파라미터·쿼리 문자열·헤더를 추출해 이벤트를 만들고, Lambda가 그 이벤트를 처리합니다. DynamoDB도 서버리스이고 낮은 지연 시간으로 응답하도록 만들어져 **연결 풀이 필요 없습니다** |

이벤트 기반 애플리케이션은 다른 서비스·시스템도 관찰할 수 있는 이벤트로 통신하고 **이벤트 생산자는 어떤 소비자가 수신 중인지 알지 못하므로**, 기존 워크플로를 방해하지 않고 확장하기가 더 쉽습니다.

> — 출처: [Transitioning to event-driven architecture](https://docs.aws.amazon.com/serverless/latest/devguide/serverless-transition.html)

🆕 백서는 여기에 세 번째 패턴을 더합니다. API 기반·이벤트 기반 두 범주에 더해, 백서는 **API 기반(API driven) · 이벤트 기반(event driven) · 데이터 스트리밍(data streaming)** 세 가지 마이크로서비스 패턴을 다룹니다.

> — 출처: [Implementing Microservices on AWS](https://docs.aws.amazon.com/whitepapers/latest/microservices-on-aws/microservices-on-aws.html)

### 3.6 이벤트 기반 통합을 구현하는 서비스 🆕

애플리케이션 통합 계층에는 Amazon EventBridge·Amazon SQS·Amazon SNS가 있습니다. 실제로 무엇을 고르는지가 설계 결정이므로 두 가지를 보강합니다.

#### EventBridge의 세 가지 처리 방식

EventBridge는 이벤트를 사용해 애플리케이션 구성 요소를 연결하는 서버리스 서비스입니다. 문서는 이벤트 기반 아키텍처를 "이벤트를 내보내고 이에 응답하며 함께 동작하는 소결합 소프트웨어 시스템을 구축하는 방식"이라고 정의합니다.

| 방식 | 형태 | 언제 쓰나 |
|---|---|---|
| 이벤트 버스(Event buses) | 이벤트를 받아 **0개 이상의 대상**으로 전달하는 라우터 | 여러 소스에서 여러 대상으로 라우팅. 전달 전에 선택적으로 이벤트를 변환할 수 있습니다 |
| 파이프(EventBridge Pipes) | **지점 간(point-to-point)** 통합. 각 파이프가 단일 소스에서 이벤트를 받아 처리한 뒤 단일 대상으로 전달 | 고급 변환·보강이 필요한 1:1 연결 |
| 스케줄러(EventBridge Scheduler) | cron·rate 표현식으로 반복 일정을 만들거나 일회성 호출을 구성 | 유연한 전달 시간 창, 재시도 한도, 실패한 API 호출의 최대 보존 시간을 설정할 수 있습니다 |

파이프와 이벤트 버스는 함께 쓰는 경우가 많습니다. 예를 들어 DynamoDB 스트림을 소스로 하는 파이프의 대상을 이벤트 버스로 둡니다.

> — 출처: [What Is Amazon EventBridge?](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-what-is.html)

🔄 오래된 자료나 기존 코드에서 **Amazon CloudWatch Events**를 만나면 당황할 필요가 없습니다. Amazon EventBridge는 이전에 Amazon CloudWatch Events라고 불렸습니다. CloudWatch Events에서 만든 기본 이벤트 버스와 규칙이 EventBridge 콘솔에도 표시되고, EventBridge가 **동일한 CloudWatch Events API를 사용**하므로 CloudWatch Events API를 쓰는 코드는 그대로 동작합니다. 다만 EventBridge에 추가되는 새 기능(파트너 이벤트, 스키마 레지스트리, EventBridge Pipes 등)은 CloudWatch Events에 추가되지 않습니다.

> — 출처: [EventBridge is the evolution of Amazon CloudWatch Events](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-cwe-now-eb.html)

#### SQS 큐 유형 선택

마이크로서비스 사이에 큐를 둘 때는 두 유형 중 하나를 골라야 합니다. 이것이 실제 결정 지점입니다.

| 항목 | 표준 큐 | FIFO 큐 |
|---|---|---|
| 처리량 | 작업마다 초당 **거의 무제한** API 호출 | 배치를 쓰면 API 메서드당 초당 최대 **3,000 메시지**(초당 300 API 호출 × 배치 10건). 배치를 쓰지 않으면 API 메서드당 초당 최대 **300 API 호출** |
| 고처리량 모드 | — | 메시지 그룹 내 순서를 완화하는 조건으로 초당 최대 **30,000 트랜잭션**까지 확장 |
| 전달 보장 | **최소 1회 전달(at-least-once)**. 메시지가 두 번 이상 전달될 수 있어 애플리케이션이 **멱등 연산**으로 중복을 처리하도록 설계해야 합니다 | **정확히 한 번 처리(exactly-once)**. 각 메시지를 한 번 전달하고 처리·삭제할 때까지 유지 |
| 중복 제거 | — | `MessageDeduplicationId` 또는 콘텐츠 기반 중복 제거 |
| 순서 | **최선 노력 순서(best-effort ordering)**. 순서가 보장되지 않습니다 | 각 메시지 그룹 안에서 **보낸 순서대로** 수신. 메시지를 여러 그룹으로 분산하면 그룹 내 순서를 유지하면서 병렬 처리할 수 있습니다 |

> — 출처: [Amazon SQS queue types](https://docs.aws.amazon.com/AWSSimpleQueueService/latest/SQSDeveloperGuide/sqs-queue-types.html)

### 3.7 모놀리스 디커플링과 스트랭글러 피그 패턴

디커플링의 지침은 다음과 같습니다.

- 분리에 적합한 작은 서비스부터 소규모로 시작
- 모놀리스에 대한 종속성 최소화
- 복잡한 종속성은 초기에 분리
- 자주 변경되는 기능 분리하기
- 예: 스트랭글러 피그 설계 패턴 — 단계적 접근 방식 / 기존 기능을 점진적으로 마이크로서비스로 교체

강조할 전제는 이렇습니다. 모놀리스 애플리케이션을 디커플링하려면 점진적으로 실행하는 면밀한 프로세스가 필요합니다.

문서는 스트랭글러 피그 패턴을 Martin Fowler가 소개한, 크고 모놀리식한 시스템을 현대화하거나 다시 작성할 때 **위험을 관리하는 방법**으로 기술합니다. 절차는 다음과 같습니다.

| 단계 | 내용 |
|---|---|
| 1 | 다른 시스템이 웹 서비스에 종속성을 갖는 지점에 **프록시**를 세웁니다 |
| 2 | 처음에는 프록시가 **통과(pass-through)** 동작을 하고, 기존 모놀리식 애플리케이션 서비스가 구현을 채웁니다 |
| 3 | 모놀리스와 분리된 **새 서비스**를 만들고 프록시의 구현을 그 새 서비스로 넘깁니다 |
| 4 | 2~3을 레거시 시스템의 모든 기능이 새 서비스로 이전될 때까지 반복합니다. 그 시점에 **레거시 시스템을 폐기**할 수 있습니다 |

문서가 제시하는 모범 사례는 위 지침과 겹치면서 한 가지를 더합니다.

| 모범 사례 | 위 지침과의 관계 |
|---|---|
| 테스트 커버리지가 좋고 기술 부채가 적은 구성 요소를 고르기 | 🆕 위 지침에 없는 기준입니다 |
| 확장성 요구가 있는 구성 요소부터 시작하기 | "분리에 적합한 작은 서비스부터 소규모로 시작"과 맞물립니다 |
| 비즈니스 요구가 자주 바뀌고 자주 배포되는 구성 요소를 고르기 | "자주 변경되는 기능 분리하기"와 같습니다 |

> — 출처: [The strangler fig pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/modernization-aspnet-web-services/fig-pattern.html)

이 주제를 더 깊게 다루는 과정으로 `Advanced Developing on AWS`가 있습니다.

### 3.8 분산 트랜잭션과 사가 오케스트레이션 패턴 🆕

[6.1절](#61-복잡한-분산-워크플로의-오케스트레이션)의 "노트 게시 워크플로"는 성공 경로와 좋음·나쁨 분기만 보여 줍니다. 여러 서비스에 걸친 트랜잭션이 **중간에 실패했을 때 이미 커밋된 변경을 되돌리는 방법**은 그 흐름만으로는 드러나지 않습니다. 이 자리를 채우는 것이 사가 오케스트레이션 패턴입니다.

| 항목 | 내용 |
|---|---|
| 문제 | 관계형 데이터베이스는 **2단계 커밋(2PC)** 으로 트랜잭션 일관성을 유지하지만, 서비스별 데이터베이스(database-per-service) 설계를 따르는 분산 시스템에서는 2PC를 쓸 수 없습니다 |
| 해법 | 중앙 코디네이터(**오케스트레이터**)가 여러 서비스에 걸친 분산 트랜잭션을 조정해 데이터 무결성을 유지합니다 |
| 실패 시 | 어느 단계가 실패하면 오케스트레이터가 **보상 트랜잭션(compensatory transaction)** 을 실행해 데이터를 초기 상태로 되돌립니다 |
| 구현 | 트랜잭션이 여러 데이터베이스에 분산된 경우 **AWS Step Functions**로 사가 오케스트레이션을 구현할 수 있고, 샘플 솔루션은 Standard 워크플로를 씁니다 |

공짜는 아닙니다. 문서가 나열하는 고려 사항은 다음과 같습니다.

| 고려 사항 | 내용 |
|---|---|
| 복잡성 | 보상 트랜잭션·재시도가 애플리케이션 코드를 복잡하게 만듭니다 |
| 최종 일관성 | 트랜잭션이 즉시 일관되지 않습니다 |
| 멱등성 | 사가 참여자는 **멱등**이어야 합니다 |
| 트랜잭션 격리 부재 | 동시 오케스트레이션이 오래된 데이터를 낳을 수 있어 **시맨틱 락**을 권장합니다 |
| 관찰 가능성 · 지연 시간 · 단일 실패 지점 | 오케스트레이터가 단일 실패 지점이 될 수 있습니다. Step Functions를 쓰면 내장 내결함성과 각 AWS 리전 내 여러 가용 영역에 걸친 서비스 용량 유지로 이 문제가 완화됩니다 |

> — 출처: [Saga orchestration pattern](https://docs.aws.amazon.com/prescriptive-guidance/latest/cloud-design-patterns/saga-orchestration.html)

### 3.9 소프트웨어 전달: DevOps

모놀리스의 단일 파이프라인과 마이크로서비스의 서비스별 독립 파이프라인을 대비하면 이렇습니다.

| 구분 | 파이프라인 |
|---|---|
| 모놀리스 | 여러 팀이 공유하는 **단일** 배포 파이프라인(구축 → 테스트 → 릴리스 → 모니터링) |
| 마이크로서비스 | 서비스마다 **독립** 파이프라인 |

이 대비를 풀어 설명하면 이렇습니다.

> 기존 애플리케이션에는 여러 팀이 공유하는 단일 배포 파이프라인이 있습니다. 이러한 프로세스는 대부분 병목 현상을 유발합니다. 빠르게 움직일 수 있는 권한이 있는 팀은 새 기능을 지속적으로, 대부분의 경우 하루에 수차례 배포할 수 있습니다.
> 하루에 수차례 배포하는 애플리케이션을 운영하는 방식은 1년에 한두 차례 배포하는 애플리케이션의 가동 방식과는 다릅니다. DevOps 모델에서는 개발 및 운영 팀이 서비스 소유권과 공동 책임을 가집니다.

백서도 같은 방향으로 기술합니다. 모놀리스에서 마이크로서비스로의 전환은 조직 운영 방식에도 영향을 주어 **빠른 주기로 일하는 애자일 개발을 촉진**하고, 팀은 서비스의 생성부터 배포·유지 관리까지 전적인 책임을 집니다.

> — 출처: [Implementing Microservices on AWS](https://docs.aws.amazon.com/whitepapers/latest/microservices-on-aws/microservices-on-aws.html)

## 4. 서버리스 운영 모델

### 4.1 서버리스 컴퓨팅이란

서버리스 컴퓨팅의 정의는 다음과 같습니다.

> 서버리스 컴퓨팅을 사용하면 서버를 고려하지 않고도 애플리케이션과 서비스를 구축하고 실행할 수 있습니다. 서버리스 애플리케이션에서는 사용자가 서버를 프로비저닝, 크기 조정, 관리할 필요가 없습니다. 거의 모든 유형의 애플리케이션 또는 백엔드 서비스에 대해 서비스를 빌드할 수 있습니다. 애플리케이션을 고가용성으로 실행하고 크기 조정하는 데 필요한 모든 작업이 자동으로 처리됩니다.

AWS 서버리스 제품 페이지도 같은 세 가지를 서버리스 기술의 특징으로 듭니다. **자동 크기 조정, 내장 고가용성, 사용량 기반(pay-for-use) 과금 모델**이며, 이 기술이 용량 프로비저닝·패치 같은 인프라 관리 작업을 없애 주므로 고객에게 도움이 되는 코드 작성에 집중할 수 있다고 기술합니다.

> — 출처: [Serverless on AWS](https://aws.amazon.com/serverless/)

백서는 서버리스를 다섯 가지 원칙으로 특징짓습니다.

| 원칙 | 내용 |
|---|---|
| 인프라 관리 없음 | 프로비저닝·관리할 인프라가 없습니다 |
| 자동 크기 조정 | 소비 단위에 따라 자동으로 크기가 조정됩니다 |
| 과금 | `Pay for value` 과금 모델 |
| 가용성 | 내장 가용성·내결함성 |
| 아키텍처 | 이벤트 기반 아키텍처(EDA) |

> — 출처: [Implementing Microservices on AWS](https://docs.aws.amazon.com/whitepapers/latest/microservices-on-aws/microservices-on-aws.html)

### 4.2 서버리스에서 없어지는 작업 🔄

서버리스로 넘어가면 없어지는 운영 작업과 그대로 남는 작업이 있습니다. 일부 원본 자료는 "기존 배포 및 운영"과 "서버리스 배포 및 운영"을 두 목록으로 나란히 놓으면서 서버리스 쪽에서 없어지는 작업을 취소선으로만 구분해, 텍스트로 옮기면 두 목록이 같아 보이는 문제가 있습니다.

아래 표는 "서버리스 애플리케이션에서는 사용자가 서버를 프로비저닝, 크기 조정, 관리할 필요가 없다"는 정의를 근거로 두 목록을 구분한 것입니다. 외부 문서로 판별할 성질의 사실이 아니므로 별도 근거는 붙이지 않았습니다([10.1절](#101-교재와-다른-점)).

| 기존 배포·운영에서 하던 일 | 서버리스에서는 |
|---|---|
| 인스턴스 프로비저닝 | 없어집니다 |
| OS 업데이트 | 없어집니다 |
| 애플리케이션 플랫폼 설치 | 없어집니다 |
| 애플리케이션 구축 및 배포 | **남습니다.** 여전히 코드를 만들고 배포합니다 |
| Auto Scaling 및 로드 밸런싱 구성 | 없어집니다. 크기 조정이 서비스에 내장되어 있습니다 |
| 지속적인 서버 패치, 보안 및 모니터링 | 서버 패치가 없어집니다. 애플리케이션 보안·모니터링은 남습니다 |
| 애플리케이션 모니터링 및 유지 관리 | **남습니다.** 대상이 서버가 아니라 애플리케이션으로 좁아집니다 |

이렇게 얻는 결과는 이렇습니다. 이러한 오버헤드가 줄어들면 개발자는 확장 가능하고 신뢰할 수 있는 제품 개발에 더 많은 시간과 노력을 투자할 수 있습니다.

### 4.3 서버리스 컴퓨팅의 이점

서버리스 컴퓨팅의 이점은 크게 네 항목으로 요약되고, 이를 다섯 항목으로 풀어 정리하면 다음과 같습니다.

| 요약 | 풀어 쓴 항목 |
|---|---|
| 프로비저닝하거나 관리할 서버가 없음 | 프로비저닝, 모니터링 또는 관리할 인프라가 없음 |
| 사용량에 따른 크기 조정 | 확장성 및 내결함성이 내장됨 |
| 유휴 서버 비용은 거의 지불하지 않음 | 유휴 상태에 대해서는 비용을 지불하지 않음, 요청 기반 요금제 |
| 고가용성 및 내결함성 내장 | 손쉬운 작성, 배포 및 보안 |
| — | 모범 사례(이벤트, 무상태 방식 함수) 활성화 |

보충 설명 중 크기 조정 부분이 특히 중요합니다.

> 애플리케이션 크기를 자동으로 조정할 수 있습니다. 또는 개별 서버 단위가 아니라 사용 단위(예: 처리량, 메모리)를 설정/해제하여 용량을 조정함으로써 애플리케이션을 크기 조정할 수도 있습니다.
> 서버리스 애플리케이션은 가용성과 내결함성이 내장되어 있습니다. 애플리케이션을 실행하는 서비스가 기본적으로 대신 제공하므로 이러한 기능을 설계할 필요가 없습니다.

### 4.4 서버리스 애플리케이션 스택 🔄

서버리스 애플리케이션 스택은 아홉 개 계층에 서비스를 배치합니다.

| 계층 | 서비스 |
|---|---|
| 컴퓨팅 | AWS Lambda, AWS Fargate |
| API 프록시 | Amazon API Gateway, AWS AppSync |
| 애플리케이션 통합 | Amazon EventBridge, Amazon SQS, Amazon SNS |
| 오케스트레이션 | AWS Step Functions |
| 데이터베이스 | Amazon DynamoDB, Amazon Aurora |
| 스토리지 | Amazon S3, Amazon EFS |
| 분석 | Amazon Kinesis, Amazon Athena |
| 개발자 도구 | AWS 도구 및 SDK |
| 가시성 | Amazon CloudWatch, AWS X-Ray |

🔄 여기에는 자료 안에서 어긋나는 지점이 하나 있습니다. 일부 원본 자료는 **"사용자 스택의 3가지 계층"** 이라며 컴퓨팅 · 애플리케이션 통합 · 데이터 저장 세 가지만 나열하는데, AWS Step Functions를 "애플리케이션 통합"에 넣기도 하고 "오케스트레이션"으로 따로 두기도 해 서로 어긋납니다. 이 문서는 9개 계층을 기준으로 정리하고, 3계층은 그중 핵심 세 축으로 봅니다. 외부 문서로 판별할 성질의 사실이 아니므로 별도 근거는 붙이지 않았습니다([10.1절](#101-교재와-다른-점)).

| 핵심 3계층 | 나열되는 서비스 | 9계층에서의 대응 계층 |
|---|---|---|
| 컴퓨팅 | AWS Lambda, AWS Fargate | 컴퓨팅 |
| 애플리케이션 통합 | Amazon EventBridge, AWS Step Functions, Amazon SQS, Amazon SNS | 애플리케이션 통합 + 오케스트레이션 |
| 데이터 저장 | Amazon S3, Amazon DynamoDB, Amazon EFS, Amazon Aurora | 데이터베이스 + 스토리지 |

프로덕션 이후 수명 주기를 지원하는 서비스로는 Amazon CloudWatch와 AWS X-Ray가 더해집니다.

이 스택에서 Step Functions가 Lambda를 호출하는 관계는 Lambda 쪽 문서에서도 확인됩니다. "Lambda 함수를 호출할 수 있는 서비스" 표에서 **AWS Step Functions는 동기 또는 비동기 호출로 분류**되고, Amazon EventBridge는 이벤트 버스·규칙이 비동기, 파이프가 동기 또는 비동기로 분류됩니다. 한 함수에 여러 트리거를 둘 수 있고 각 트리거는 독립적인 클라이언트처럼 동작하며, Lambda가 함수에 전달하는 각 이벤트에는 하나의 트리거 데이터만 담깁니다. 트리거는 Lambda가 아니라 **이벤트를 생성하는 서비스가 저장·관리**합니다.

> — 출처: [Invoking Lambda with events from other AWS services](https://docs.aws.amazon.com/lambda/latest/dg/lambda-services.html)

### 4.5 자동 크기 조정에도 한도가 있다 🆕

서버리스는 "사용량에 따른 크기 조정"과 "애플리케이션 크기를 자동으로 조정"을 내세우지만, 그 자동 크기 조정이 어떤 한도 안에서 일어나는지는 잘 드러나지 않습니다. 모듈 9에서 확인한 Lambda 동시성 개념을 여기서 다시 씁니다.

| 항목 | 내용 |
|---|---|
| 동시성이란 | Lambda 함수가 **동시에 처리 중인 진행 중 요청 수**입니다. 동시 요청마다 Lambda가 실행 환경 인스턴스를 별도로 프로비저닝합니다 |
| 계정 한도 | 리전당 총 동시성 한도는 **기본 1,000**이고 증액 요청할 수 있습니다 |
| 계산식 | 동시성 = (초당 평균 요청 수) × (평균 요청 처리 시간(초)) |
| 예약된 동시성 | 계정 동시성의 일부를 그 함수에만 예약합니다. **구성 자체에는 추가 요금이 없습니다** |
| 프로비저닝된 동시성 | 미리 초기화한 실행 환경 인스턴스 수입니다. 콜드 스타트 지연을 줄이며 **추가 요금이 발생**합니다 |

즉 "무한히 자동으로 늘어난다"가 아니라 "계정 한도 안에서 자동으로 늘어난다"입니다. 마이크로서비스마다 독립적으로 크기를 조정한다는 이점도 같은 계정 한도를 공유한다는 점을 함께 알아야 합니다.

> — 출처: [Understanding Lambda function scaling](https://docs.aws.amazon.com/lambda/latest/dg/lambda-concurrency.html)

### 4.6 Lambda 와 Fargate 중 무엇을 고르나 🆕

컴퓨팅 계층에는 Lambda와 Fargate가 나란히 놓입니다. AWS 결정 안내서가 둘의 차이를 정리합니다. 두 서비스는 운영 부담 감소, 사용량 기반 과금, 빠른 배포, 내장 고가용성, 단순화된 컴플라이언스, 코드 집중이라는 이점을 **공유**합니다.

| 항목 | AWS Fargate | AWS Lambda |
|---|---|---|
| 무엇인가 | **컨테이너용** 서버리스 컴퓨팅 엔진. 주로 Amazon ECS와 함께 씁니다 | 이벤트에 응답해 코드를 **함수**로 실행합니다 |
| 적합한 워크로드 | 장기 실행 애플리케이션, 마이크로서비스, 배치 처리 | 이벤트 기반 처리 |
| 실행 시간 제한 | **하드 제한이 없습니다** | 호출당 **15분** |
| 상태 관리 | 컨테이너가 실행 중 **메모리 상태를 유지**할 수 있습니다 | 설계상 **스테이트리스**여서 외부 저장소가 필요합니다 |
| 동시성 한도 | 클러스터 용량 기반 | 기본 1,000(증액 가능) |

Serverless Developer Guide도 같은 판단 기준을 제시합니다. 마이크로서비스가 주로 **배치 데이터 처리**에 쓰인다면 Fargate에 컨테이너 애플리케이션으로 배포하는 것이 더 적절할 수 있고, **온디맨드 데이터 처리**가 필요한 애플리케이션에는 Lambda 함수를 배포·유지하는 것이 훨씬 간단합니다.

> — 출처: [AWS Fargate or AWS Lambda](https://docs.aws.amazon.com/decision-guides/latest/decision-guides/fargate-or-lambda.html)

## 5. 애플리케이션 빌드

### 5.1 과정에서 구축한 애플리케이션

과정 전체에서 만든 애플리케이션을 한 장에 모으면 이렇습니다. 이 과정에서 구축한 애플리케이션은 클라우드 네이티브이자 서버리스인 모던 애플리케이션입니다.

| 요소 | 내용 |
|---|---|
| 최종 사용자 | 웹 사이트 호스팅 / MP3 호스팅 / 애플리케이션 API 호출 |
| 애플리케이션 기능 | List / Search / Delete / Create·Update / Dictate |
| AWS 서비스 | Amazon API Gateway, Amazon Cognito, IAM, DynamoDB, Amazon Polly, AWS X-Ray, AWS SAM, Amazon CloudWatch |

무엇이 없는지가 이 애플리케이션의 성격을 가장 잘 보여 줍니다. **서버리스이기 때문에 로드 밸런서와 서버가 없습니다.**

이 애플리케이션의 진입점인 API Gateway는 모듈 10에서 다뤘습니다. API Gateway는 REST API와 HTTP API를 모두 제공하며 기능·요금이 다르고, 문서는 두 유형의 기능을 나란히 비교합니다. 어느 유형을 고르느냐가 이 애플리케이션의 진입점 설계입니다.

> — 출처: [Choose between REST APIs and HTTP APIs](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-vs-rest.html)

### 5.2 이 애플리케이션의 모던 애플리케이션 특징

이 애플리케이션에 적용된 모던 애플리케이션의 특징은 여섯 가지입니다. 각 항목이 이 애플리케이션의 어디에서 나타나는지를 붙여 두면 훨씬 잘 읽힙니다.

| 특징 | 이 애플리케이션에서 |
|---|---|
| API 기반 | 최종 사용자가 API Gateway를 통해 애플리케이션 API를 호출합니다 |
| 독립형 기능 | List / Search / Delete / Create·Update / Dictate 가 각각 독립된 기능입니다 |
| 분리형 구성 요소 | 기능마다 Lambda 함수가 분리되어 있습니다 |
| 기술에 구애받지 않음 | 기능마다 런타임을 따로 고를 수 있습니다 |
| 독립형 배포 | 기능을 개별적으로 배포할 수 있습니다 |
| 서버리스 | 로드 밸런서와 서버가 없습니다 |

여기서 "그 밖에 할 수 있는 일에는 무엇이 있는가?"라는 물음이 남습니다. 다음 장의 Step Functions가 그 답 중 하나입니다. 기능이 늘어나면 기능 사이의 순서·분기·병렬·재시도를 누군가 관리해야 하고, 그것을 코드로 쓰는 대신 워크플로로 만드는 것이 오케스트레이션입니다.

## 6. AWS Step Functions

### 6.1 복잡한 분산 워크플로의 오케스트레이션

한 줄로 요약하면 이렇습니다. 분산된 태스크의 상태를 관리하면서 애플리케이션 코드는 줄이고 복원력은 개선합니다.

문제부터 짚으면 이렇습니다.

> 일반적으로 모던 클라우드 애플리케이션은 다수의 서비스 및 구성 요소로 구성됩니다. 애플리케이션 규모가 커지면 모든 구성 요소의 상호 작용을 조율하기 위해 점점 더 많은 코드를 작성해야 합니다.

대표적인 예가 "노트 게시 워크플로"입니다. 흐름은 다음과 같습니다.

```text
클라이언트 --POST--> API Gateway --시작--> 워크플로
                                              |
                        +---------- 병렬 실행 ----------+
                        |                               |
                  로그 기록                    감정 탐지(Comprehend)
                        |                               |
                        +--------------+----------------+
                                       |
                              [ 좋은가 나쁜가? ]
                                 /            \
                             좋음              나쁨
                               |                |
                         트랜잭션 기록   관리자 알림(SES)
```

이 흐름의 주제는 한 문장으로 정리됩니다. AWS Step Functions는 이러한 상호 작용의 서버리스 오케스트레이션을 제공합니다.

이 흐름에서 클라이언트의 POST를 받는 API Gateway는 모듈 10에서 다룬 그 서비스입니다. API Gateway는 Step Functions의 최적화 통합 대상이기도 하고, 동기 Express 워크플로를 호출하는 진입점으로도 쓸 수 있습니다([6.4절](#64-워크플로-유형-standard-와-express) · [8.2절](#82-최적화-통합과-aws-sdk-통합)).

> — 출처: [Choose between REST APIs and HTTP APIs](https://docs.aws.amazon.com/apigateway/latest/developerguide/http-api-vs-rest.html)

### 6.2 비즈니스 로직 오케스트레이션 패턴

비즈니스 로직 오케스트레이션 패턴은 여섯 가지입니다. 각 패턴이 실제로 어떤 상태 타입으로 구현되는지를 오른쪽에 붙였습니다.

| 패턴 | 표기 | 구현하는 상태·필드 |
|---|---|---|
| 순차 | Sequential 태스크 (A → B) | `Task` 상태의 `Next` 필드 |
| 선택 | 데이터에 따라 태스크 Choice (A → ? → B / C) | `Choice` 상태 ([7.5절](#75-choice-상태)) |
| 재시도 | 실패한 태스크 Retry (A) | `Retry` 필드 ([7.8절](#78-오류-처리-retry-와-catch)) |
| 병렬 | Parallel 태스크 (A · B · C) | `Parallel` 상태, 또는 배열 반복이면 `Map` 상태 ([7.6절](#76-map-상태-inline-과-distributed)) |
| 대기 | Wait 기간/시간/동적 (A) | `Wait` 상태 |
| 예외 처리 | Try/Catch/Finally (A) | `Catch` 필드 ([7.8절](#78-오류-처리-retry-와-catch)) |

판단 기준은 이렇습니다. 비즈니스 로직, 재시도 및 시간 초과를 처리하는 Lambda 함수로 코드를 작성하는 대신 Step Functions를 쓸 수 있습니다. 이 선택에는 비용이 따라오므로 [6.6절](#66-요금-모델)의 과금 모델을 함께 보세요.

### 6.3 Step Functions 의 정의

Step Functions의 정의는 공식 문서와 일치합니다. 용어를 정확히 구분하는 것이 이 모듈에서 가장 중요합니다.

| 용어 | 정의 |
|---|---|
| 상태 머신(state machine) | Step Functions에서 상태 머신은 **워크플로**라고 불리며 이벤트 기반 단계의 연속입니다 |
| 상태(state) | 워크플로의 **각 단계**를 상태라고 합니다 |
| 태스크(task) | **태스크 상태**는 다른 AWS 서비스가 수행하는 작업 단위를 나타냅니다 |
| 실행(execution) | **실행 중인 워크플로 인스턴스**를 실행이라고 합니다 |
| 활동(Activities) | 상태 머신 태스크의 작업은 Step Functions **외부에 존재하는 작업자**로도 수행할 수 있습니다 ([8.5절](#85-활동-작업자)) |

문서는 Step Functions로 워크플로를 만들어 분산 애플리케이션을 구축하고, 프로세스를 자동화하고, 마이크로서비스를 오케스트레이션하고, 데이터·기계 학습 파이프라인을 만든다고 기술합니다. 콘솔에서 워크플로를 시각화·편집·디버깅하고 각 단계의 상태를 검사할 수 있습니다.

워크플로가 관리하는 것은 다음 다섯 가지입니다.

| 워크플로가 관리하는 것 |
|---|
| 장애 |
| 재시도 |
| 병렬화 |
| 서비스 통합 |
| 관찰 기능 |

> — 출처: [What is Step Functions?](https://docs.aws.amazon.com/step-functions/latest/dg/welcome.html)

### 6.4 워크플로 유형: Standard 와 Express 🆕

워크플로 유형은 자주 놓치는 지점입니다. 상태 머신을 만들 때 **Standard(기본값) 또는 Express를 반드시 선택해야 하고, 이 유형은 생성 후 변경할 수 없습니다.** 실습에서 첫 화면에 나오는 선택입니다.

| 항목 | Standard | Express |
|---|---|---|
| 최대 실행 시간 | **1년** | **5분** |
| 실행 모델 | **exactly-once** | 비동기는 **at-least-once**, 동기는 **at-most-once** |
| 실행 이력 | 실행 완료 후 최대 **90일**간 Step Functions API로 전체 이력 조회 가능(할당량 요청으로 30일로 축소 가능) | Step Functions가 저장하지 않으므로 **CloudWatch Logs 로깅을 켜야** 합니다 |
| 과금 | **상태 전환 수** | **실행 수 · 실행 시간 · 메모리 소비** |
| 서비스 통합 | 모든 통합, 모든 통합 패턴 | 모든 서비스 통합. 단 **`.sync`(Run a Job)·`.waitForTaskToken`(Callback) 패턴 미지원** |
| Distributed Map | 지원 | **미지원** |
| 활동(Activities) | 지원 | **미지원** |
| redrive | 지원(14일) | **미지원** |

무엇을 고르는가의 기준은 실행 모델입니다.

| 워크로드 | 선택 | 이유 |
|---|---|---|
| EMR 클러스터 시작, 결제 처리 같은 **비멱등** 작업 | Standard | exactly-once 여야 중복 실행이 없습니다 |
| DynamoDB `PUT` 같은 **멱등** 작업, 고빈도 이벤트 처리 | Express | at-least-once 로 중복이 발생해도 결과가 같습니다 |

Express에는 동기(`StartSyncExecution`)와 비동기(`StartExecution`) 두 종류가 있습니다. 콘솔에서 `StartSyncExecution` 요청은 **60초 후 만료**되므로, 최대 5분까지 가는 동기 실행에는 SDK나 CLI를 써야 합니다.

> — 출처: [Choosing workflow type in Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/choosing-workflow-type.html)

### 6.5 워크플로를 정의하는 방법 🔄

워크플로를 정의하는 과정은 세 단계입니다.

| 단계 | 표기 |
|---|---|
| 정의 | JSON - Amazon States 언어 |
| 시각화 | State Function Workflow Studio |
| 실행 및 모니터링 | — |

🔄 두 가지를 교정합니다.

**첫째, 도구 이름.** 일부 원본 자료는 이 도구를 "State Function Workflow Studio"로 적기도 하지만 공식 이름은 **Workflow Studio**입니다. 또 콘솔 전용으로 알려지기 쉽지만, 현재는 Step Functions 콘솔 외에 **AWS Infrastructure Composer** 안에서와 **VS Code용 AWS Toolkit**을 통해서도 쓸 수 있고, VS Code에서는 개별 상태를 테스트할 수도 있습니다.

| Workflow Studio | 내용 |
|---|---|
| 무엇인가 | Step Functions 콘솔에서 워크플로를 편집할 때 쓰는 **시각적 도구**입니다. 상태를 캔버스에 끌어다 놓아 워크플로를 만듭니다 |
| 무엇을 하나 | 상태 추가·편집·구성, 입력·출력 필터 설정, 결과 변환, 오류 처리 설정 |
| 정의 생성 | 상태를 수정하면 Workflow Studio가 상태 머신 정의를 **검증하고 자동 생성**합니다 |
| 세 가지 모드 | **Design · Code · Config** |
| States browser — Actions 탭 | 서드 파티 HTTP 엔드포인트와 AWS API에 연결되는 **태스크 상태** 목록 |
| States browser — Flow 탭 | `Choice` · `Parallel` · `Map` · `Pass` · `Wait` · `Success` · `Fail` **흐름 상태** |
| States browser — Patterns 탭 | 바로 쓸 수 있는 **재사용 가능한 구성 블록** |

> — 출처: [Developing workflows in Step Functions Workflow Studio](https://docs.aws.amazon.com/step-functions/latest/dg/workflow-studio.html)

**둘째, ASL 참조 문서.** ASL 링크로 AWS 도메인이 아닌 `states-language.net`만 알려지기 쉽습니다. AWS 공식 문서에도 ASL 페이지가 있고, 그 페이지가 Amazon States Language Specification과 ASL 코드를 검증하는 `Statelint` 도구를 함께 참조합니다.

| Amazon States Language | 내용 |
|---|---|
| 무엇인가 | 상태 머신을 정의하는 **JSON 기반 구조화 언어**입니다 |
| 파일 확장자 | Step Functions 콘솔 **밖에서** 상태 머신을 정의하는 경우 정의 파일은 **`.asl.json`** 확장자로 저장해야 합니다 |
| 현재 문서의 예제 | `QueryLanguage`를 **JSONata**로 설정하고 `Choice` 상태에서 `Condition` 필드에 JSONata 표현식을 씁니다 |

> — 출처: [Using Amazon States Language to define Step Functions workflows](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-amazon-states-language.html)

실행·모니터링 경로는 문서와 일치합니다. AWS Management Console에서는 실행 중인 워크플로를 시각화할 수 있고, Amazon CloudWatch 지표, CloudWatch Logs, AWS X-Ray 및 기타 도구로 워크플로를 기록하고 모니터링할 수 있습니다. 그 "기타 도구"가 무엇인지는 [9.2절](#92-로깅과-모니터링)에 있습니다.

### 6.6 요금 모델 🆕

Step Functions의 과금 모델은 흔히 간과됩니다. 그런데 [6.2절](#62-비즈니스-로직-오케스트레이션-패턴)에서 재시도·시간 초과를 처리하는 Lambda 함수 대신 Step Functions를 권했으므로, **재시도가 무엇으로 과금되는지**를 함께 알아야 설계 판단을 할 수 있습니다.

| 항목 | Standard | Express |
|---|---|---|
| 과금 기준 | **상태 전환** 수 | **요청 수 + 지속 시간** |
| 상태 전환이란 | 워크플로의 한 단계가 실행될 때마다 하나로 계산합니다. **재시도를 포함한** 모든 상태 전환 총수로 과금합니다 | — |
| 재시도의 영향 | 워크플로 어느 단계에 재시도 오류 처리를 넣으면 **각 재시도가 추가 상태 전환으로 과금**됩니다 | — |
| 지속 시간 계산 | — | 실행을 시작한 시점부터 완료·종료될 때까지를 **가장 가까운 100ms로 올림** |
| 메모리 과금 | — | **64MB 단위**. 메모리 소비는 워크플로 정의 크기, `Map`·`Parallel` 상태 사용, 실행(페이로드) 데이터 크기에 따라 달라집니다 |
| 콘솔 테스트 | — | 콘솔에서의 테스트도 **요청으로 계산**됩니다 |
| 프리 티어 | 월 **4,000건**의 무료 상태 전환. 12개월 AWS 프리 티어 기간이 끝나도 자동 만료되지 않고 기존·신규 고객 모두에게 무기한 제공 | — |

`Map` 상태의 과금은 모드에 따라 다릅니다. **Distributed Map은 반복마다 상태 전환 하나가 과금되지만 Inline Map은 각 반복 시작에 대한 상태 전환이 없습니다.** 워크플로가 다른 AWS 서비스를 쓰거나 데이터를 전송하면 그 서비스 요금이 별도로 발생합니다.

## 7. 상태 타입과 데이터 흐름

### 7.1 상태 타입 여덟 개 🔄

상태를 일곱 항목으로 세면서 **Succeed와 Fail을 한 항목으로 묶는** 경우가 있는데, 공식 워크플로 상태 참조 목록은 **여덟 개**이고, Workflow Studio는 `Task`(Actions)를 제외한 일곱 개를 Flow 상태로 분류합니다. 각 상태의 설명 자체는 문서와 일치합니다.

| 상태 | 설명 | Workflow Studio 분류 |
|---|---|---|
| `Task` | 상태 머신에 의해 수행되는 단일 작업 단위입니다 | Actions |
| `Choice` | 흐름의 적절한 분기를 선택합니다 | Flow |
| `Parallel` | 흐름 안에서 병렬 분기를 시작합니다 | Flow |
| `Map` | 상태 입력에서 어레이의 여러 항목에 대해 동일한 단계를 실행합니다 | Flow |
| `Pass` | 입력을 원 상태 그대로 또는 일부 수정된 데이터와 결합하여 출력으로 전달합니다 | Flow |
| `Wait` | 지정된 기간 동안 흐름을 지연합니다 | Flow |
| `Succeed` | Fail과 묶어 "통과/실패를 기준으로 흐름을 중단합니다"로 설명되기도 합니다 | Flow |
| `Fail` | 같음 | Flow |

모든 상태에 공통으로 적용되는 규칙입니다.

| 규칙 | 내용 |
|---|---|
| `Type` | 모든 상태는 상태 유형을 나타내는 `Type` 필드를 갖습니다 |
| `Comment` | 모든 상태가 선택적 `Comment` 필드를 가질 수 있습니다 |
| `Next` | `Succeed`·`Fail`을 제외한 모든 상태는 다음 상태를 지정하는 `Next` 필드가 필요합니다 |
| `Next`의 예외 | `Choice` 상태는 각 Choice Rule 안에 `Next`를 여러 개 가질 수 있습니다 |
| `End` | `End`를 `true`로 설정하면 **종단 상태**가 됩니다 |
| 상태 이름 | 문자열이고 **상태 머신 전체 범위에서 고유**해야 합니다 |

`Map`과 `Parallel`의 차이를 헷갈리기 쉽습니다. `Parallel`은 서로 다른 분기를 동시에 실행하고, `Map`은 **상태 입력 배열의 여러 항목에 같은 단계**를 실행합니다.

> — 출처: [Discovering workflow states](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-states.html)

### 7.2 태스크 상태의 내부 구조

태스크 상태는 "JSON 정보가 태스크 상태를 통과해 이동하는 방식"으로 이해할 수 있습니다. 상태가 호출할 수 있는 대상은 세 가지입니다.

| 호출 대상 | 이 문서 |
|---|---|
| AWS 서비스 | [8.2절](#82-최적화-통합과-aws-sdk-통합) |
| Lambda 함수 | [8.4절](#84-lambda-최적화-통합) |
| 활동 작업자 | [8.5절](#85-활동-작업자) |

데이터 흐름을 한 문장으로 정리하면 이렇습니다.

> 상태 머신에서 모든 작업은 태스크를 통해 수행됩니다. AWS Step Functions를 사용하면 여러 태스크 간의 작업을 조율할 수 있습니다. 입력 정보는 InputPath로 전달됩니다. 관련 파라미터가 확인되고 상태가 설정됩니다. 그런 다음 코드를 호출합니다. ResultPath는 출력 데이터를 이용해 결정합니다.

여기서 한 가지를 정확히 짚어야 합니다. **상태 머신에서 모든 작업은 태스크가 수행하며, 태스크가 Lambda 함수를 호출할 수도 있고 다른 서비스를 호출할 수도 있습니다.** "모든 작업을 Lambda 함수로 수행한다"가 아닙니다.

> — 출처: [What is Step Functions?](https://docs.aws.amazon.com/step-functions/latest/dg/welcome.html)

### 7.3 JSONPath 데이터 흐름 필드 다섯 개 🔄

이 필드 목록은 자료 안에서 어긋나기 쉽습니다. **일부 원본 자료는 다이어그램에 네 필드를 표기하고 본문에서는 조작 필드로 세 개를 나열하는데, 두 목록이 서로 다릅니다.**

| 필드 | 다이어그램 표기 | 본문 나열 |
|---|---|---|
| `InputPath` | 있음 | 있음 |
| `Parameters` | 있음 | 있음 |
| `ResultSelector` | **없음** | 있음 |
| `ResultPath` | 있음 | **없음** |
| `OutputPath` | 있음 | **없음** |

정확한 목록은 **다섯 개**이고, **적용 순서도 아래 순서**입니다.

| 순서 | 필드 | 하는 일 | 설명 |
|---|---|---|---|
| 1 | `InputPath` | 태스크에 전달할 JSON 입력 부분을 선택 | "태스크에 전달할 JSON 입력 부분을 결정합니다" |
| 2 | `Parameters` | 액션에 보낼 데이터를 조정 | "정보를 연결된 리소스의 API 작업으로 전달합니다" |
| 3 | (리소스 호출) | 태스크가 실제로 실행됩니다 | — |
| 4 | `ResultSelector` | 액션 결과에서 이어 나갈 부분을 선택 | 다이어그램에 없음 |
| 5 | `ResultPath` | 상태 입력과 태스크 결과의 조합을 출력으로 전달 | "출력으로 전달할 정보를 결정합니다" |
| 6 | `OutputPath` | 출력 JSON을 걸러 다음 상태로 전달할 정보를 제한 | "전달된 데이터를 필터링합니다" |

한 가지 더 알아야 할 제약이 있습니다. **상태 출력은 기본적으로 바로 다음 상태에만 전달됩니다.** 이후 단계에서 필요한 데이터는 변수에 저장하는 것을 고려하라고 문서가 안내합니다([7.4절](#74-jsonata-와-변수)).

> — 출처: [Processing input and output in Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-input-output-filtering.html)

### 7.4 JSONata 와 변수 🆕

JSONPath 기반 필드와 `$` 표기법만 다루기 쉽지만, 현재 Step Functions는 **JSONata**를 쿼리·변환 언어로 지원하고, **새 상태 머신에는 JSONata를 권장**합니다. 기존 JSONPath 예제가 지금도 동작하는 이유는 쿼리 언어를 지정하지 않은 상태 머신이 **하위 호환을 위해 JSONPath로 기본 설정**되기 때문입니다.

#### JSONata

| 항목 | 내용 |
|---|---|
| 지원 명세 | JSONata **2.0.6** 명세를 구현하며 해당 명세의 모든 내장 함수·연산자를 지원합니다. 단 `$eval`은 제공하지 않고 `$parse`를 씁니다 |
| 옵트인 | 기존 워크플로에서 JSONata를 쓰려면 **옵트인**해야 합니다. 콘솔에서 새 워크플로를 만들 때는 최상위 상태 머신 `QueryLanguage`로 JSONata를 선택하는 것이 권장됩니다 |
| 필드 수 감소 | JSONata를 선택하면 다섯 개의 JSONPath 필드(`InputPath`·`Parameters`·`ResultSelector`·`ResultPath`·`OutputPath`)가 **`Arguments`와 `Output` 두 필드로** 줄어들고 JSON 객체 키 이름에 `.$`를 쓰지 않습니다 |
| 표현식 구문 | `"{% <JSONata 표현식> %}"` 입니다. **선행·후행 공백이 있으면 검증 오류**가 납니다 |
| 점진 도입 | `QueryLanguage` 필드는 상태 머신 최상위와 **개별 상태 양쪽에** 지정할 수 있어 기존 상태 머신에 점진적으로 도입할 수 있습니다. 최상위에서 생략하면 JSONPath로 기본 설정됩니다 |
| 예약 변수 | `$states` 하나를 정의하며 `input`, `result`, `errorOutput`, `context`를 담습니다 |

#### 변수(Variables)

| 항목 | 내용 |
|---|---|
| 왜 필요한가 | 상태 출력은 **바로 다음 단계의 입력으로만** 쓸 수 있는 반면, 변수는 **이후 어느 단계에서든** 참조할 수 있습니다 |
| 크기 | 상태당 최대 **256KiB** |
| `Assign`을 쓸 수 있는 상태 | `Pass`, `Task`, `Map`, `Parallel`, `Choice`, `Wait` |
| 참조 방법 | 이름 앞에 달러 기호(`$`)를 붙입니다 |
| 이름 규칙 | Unicode Identifier 규칙을 따르고 최대 길이 **80자** |
| 범위 | **워크플로 로컬 범위**입니다. `Parallel`·`Map` 내부는 별도 범위여서 외부 범위 변수는 읽을 수 있지만 자체 변수를 따로 유지합니다 |
| 범위 제약 | 내부 범위에서 외부 범위와 **같은 이름의 변수에 할당할 수 없고**, Distributed Map 상태는 현재 외부 범위 변수를 참조할 수 없습니다. 단 `Catch`의 `Assign`은 `Parallel`·`Map`이 존재하는 외부 범위 변수에 값을 할당할 수 있습니다 |

`Assign`과 `Output` 단계는 **병렬로 수행**되므로, 변수 할당 시 변환한 데이터는 `Output` 단계에서 다시 변환해야 합니다.

> — 출처: [Transforming data with JSONata in Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/transforming-data.html)

> — 출처: [Passing data between states with variables](https://docs.aws.amazon.com/step-functions/latest/dg/workflow-variables.html)

### 7.5 Choice 상태 🆕

`Choice` 상태는 "흐름의 적절한 분기를 선택합니다"로 요약되지만, 실무에서 상태 머신을 깨뜨리는 지점이 여기라서 조금 더 봅니다.

| 필드 | 필수 여부 | 내용 |
|---|---|---|
| `Choices` | **필수** | 다음 상태를 결정하는 Choice Rule 배열입니다. **최소 하나의 규칙**을 정의해야 합니다 |
| `Default` | 선택(**권장**) | 어떤 Choice Rule도 `true`로 평가되지 않을 때 전환할 상태 이름입니다 |
| `End` | **지원하지 않음** | `Choice` 상태는 `End` 필드를 지원하지 않고 `Next`는 `Choices` 필드 안에서만 씁니다 |

가장 중요한 함정: **어떤 `Choices`도 `true`가 아니고 `Default`도 없으면 상태에서 빠져나가지 못해 상태 머신이 오류를 던집니다.** [7.7절](#77-예제-lambda-로-루프-반복하기)의 예제가 `Default: Done`을 지정한 것은 문서 권장과 맞습니다.

Choice Rule의 형태는 쿼리 언어에 따라 다릅니다.

| 쿼리 언어 | Choice Rule 구성 |
|---|---|
| JSONPath | **비교**(`Variable`과 비교 연산자 필드) + `Next`. 연산자는 `NumericEquals`, `StringEquals`, `StringGreaterThan`, `IsNull`, `IsPresent`, `StringMatches`, `TimestampEquals` 등이며, 연산자 이름 끝에 **`Path`를 붙이면** 상태 입력의 다른 값과 비교할 수 있습니다 |
| JSONata | `true`/`false`로 평가되는 JSONata 표현식인 **`Condition`** 필드 + `Next`. 규칙별 **`Assign` 블록**으로 어느 경로를 탔는지에 따라 다른 변수를 설정할 수 있습니다 |

> — 출처: [Choice workflow state](https://docs.aws.amazon.com/step-functions/latest/dg/state-choice.html)

### 7.6 Map 상태: Inline 과 Distributed 🆕

`Map` 상태는 처리 모드를 구분하지 않고 설명되기 쉽습니다. 현재 `Map` 상태에는 **두 처리 모드**가 있고, 어느 쪽을 쓰는지에 따라 동시성·입력 소스·과금이 모두 달라집니다.

| 항목 | Inline 모드(기본) | Distributed 모드 |
|---|---|---|
| 입력 | **JSON 배열만** | Amazon S3의 대규모 데이터 소스(단일 JSON·CSV 파일 또는 S3 객체 집합)도 가능 |
| 실행 단위 | 각 반복이 **Map 상태를 포함한 워크플로의 컨텍스트**에서 실행됩니다 | 각 반복이 **자체 실행 이력을 가진 하위 워크플로 실행(child workflow execution)** 으로 실행됩니다 |
| 실행 이력 | 반복 이력이 **부모 워크플로 실행 이력에 추가**됩니다 | 반복마다 별도 이력을 가집니다 |
| 동시 반복 | 최대 **40개** | 지정하지 않으면 **10,000개** 병렬 하위 워크플로 실행 |
| 워크플로 유형 | Standard · Express | **Standard 전용** |
| 실패 전파 | 어느 한 반복이 실패하면 **Map 상태가 실패하고 모든 반복이 중지**됩니다 | `Map Run` 리소스로 관리됩니다 |
| 과금 | 각 반복 시작에 대한 상태 전환이 **없습니다** | **반복마다 상태 전환 하나**가 과금됩니다 |

Distributed 모드를 써야 하는 조건은 셋 중 하나라도 해당할 때입니다.

| 조건 |
|---|
| 데이터 세트 크기가 **256KiB를 초과** |
| 워크플로 실행 이벤트 이력이 **25,000개를 초과** |
| **40개보다 많은 동시 반복**이 필요 |

Distributed 모드로 실행하면 Step Functions가 **`Map Run`** 리소스를 만들고 ARN을 할당하며 `DescribeMapRun` API로 조회할 수 있습니다. 주요 필드는 `ItemReader`, `ItemProcessor`(`ProcessorConfig`의 `Mode=DISTRIBUTED`, `ExecutionType`), `Label`, `ResultWriter`이고, 상태 머신 역할에 **`states:StartExecution`·`states:DescribeExecution` 권한**이 필요합니다.

#### 사용이 중단된 Map 필드 두 개

| 옛 필드 | 대체 필드 | 상태 |
|---|---|---|
| `Iterator` | **`ItemProcessor`** | 사용 중단(deprecated). 문서는 바꾸도록 **강력히 권장**합니다 |
| `Map` 안의 `Parameters` | **`ItemSelector`** | 사용 중단 |

주의: [7.7절](#77-예제-lambda-로-루프-반복하기)에 등장하는 `Iterator`는 **Map 상태의 필드가 아니라 Task 상태의 이름**이므로 이 사용 중단과는 무관합니다. `MaxConcurrency`로 병렬 반복 수의 상한을 지정하며, 입력 배열 항목이 40개를 넘으면 동시 반복이 제한될 가능성이 커집니다.

> — 출처: [Using Map state in Distributed mode](https://docs.aws.amazon.com/step-functions/latest/dg/state-map-distributed.html)

> — 출처: [Using Map state in Inline mode](https://docs.aws.amazon.com/step-functions/latest/dg/state-map-inline.html)

### 7.7 예제: Lambda 로 루프 반복하기 🔄

반복 패턴의 ASL 정의입니다. 원본에서 두 가지를 교정했습니다.

| 교정한 것 | 원본 | 이 문서 |
|---|---|---|
| 닫는 인용부호 | `"Next": "Iterator“` 처럼 곧은 인용부호가 아니라 **왼쪽 큰따옴표**여서 JSON으로 파싱되지 않습니다 | 곧은 인용부호로 교정 |
| 계정 ID | `arn:aws:lambda:us-east-1:12342:function:Iterate` — 계정 ID 자리가 **5자리**입니다 | 12자리 예시 값 `123456789012` |

ARN의 일반 형식은 `arn:partition:service:region:account-id:resource-id`이고 `account-id`는 리소스를 소유한 AWS 계정 ID로 **하이픈 없이 12자리**로 표기합니다(문서 예시 `123456789012`). 지원되는 `partition`은 `aws`(AWS 리전), `aws-cn`(중국 리전), `aws-us-gov`(AWS GovCloud (US) 리전)입니다. 일부 리소스의 ARN은 리전이나 계정 ID 또는 둘 다를 생략합니다.

> — 출처: [Amazon Resource Names (ARNs)](https://docs.aws.amazon.com/IAM/latest/UserGuide/reference-arns.html)

```json
{
  "Comment": "Iterator State Machine Example",
  "StartAt": "ConfigureCount",
  "States": {
    "ConfigureCount": {
      "Type": "Pass",
      "Result": { "count": 10, "index": 0, "step": 1 },
      "ResultPath": "$.iterator",
      "Next": "Iterator"
    },
    "Iterator": {
      "Type": "Task",
      "Resource": "arn:aws:lambda:us-east-1:123456789012:function:Iterate",
      "ResultPath": "$.iterator",
      "Next": "IsCountReached"
    },
    "IsCountReached": {
      "Type": "Choice",
      "Choices": [
        {
          "Variable": "$.iterator.continue",
          "BooleanEquals": true,
          "Next": "ExampleWork"
        }
      ],
      "Default": "Done"
    },
    "ExampleWork": {
      "Comment": "Your application logic, to run a specific number of times",
      "Type": "Pass",
      "Result": { "success": true },
      "ResultPath": "$.result",
      "Next": "Iterator"
    },
    "Done": {
      "Type": "Pass",
      "End": true
    }
  }
}
```

상태별 역할은 공식 튜토리얼과 일치합니다.

| 상태 | 역할 |
|---|---|
| `ConfigureCount` | 개수(`count`), 인덱스(`index`), 단계(`step`)의 기본값을 설정합니다 |
| `Iterator` | `Task` 유형입니다. 특정 ARN을 가진 리소스(여기서는 Lambda)가 작업을 수행하며 `ConfigureCount`에 구성된 값이 전달됩니다. Lambda 함수는 `count`·`index`·`step`을 받아 `index`를 `step`만큼 증가시키고, `index < count`인 Boolean `continue`와 함께 반환합니다 |
| `IsCountReached` | `Iterator`가 반환한 Boolean을 기반으로 `ExampleWork`를 다시 실행하거나 `Done`으로 이동하는 `Choice` 상태입니다 |
| `ExampleWork` | 실행 중에 수행하고자 하는 작업의 **스텁**입니다. 이 예시에서는 `Pass` 상태이고 **실제 구현에서는 `Task` 상태**가 됩니다 |
| `Done` | 실행의 마지막 상태입니다 |

이 튜토리얼 URL은 그대로 유효합니다. 문서는 이 패턴을 언제 쓰는지도 설명합니다. **상태 머신의 루프 횟수를 추적해야 할 때** 쓰며, 큰 태스크나 장기 실행을 작은 조각으로 나누거나 특정 이벤트 수 이후 실행을 끝내는 데 도움이 됩니다. 비슷한 구현으로 장기 실행을 주기적으로 종료·재시작해 Step Functions·Lambda·다른 AWS 서비스의 **서비스 할당량 초과를 피할** 수 있습니다. 현재 문서의 Lambda 런타임 선택은 Node.js입니다.

> — 출처: [Iterate a loop with a Lambda function in Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/tutorial-create-iterate-pattern-section.html)

`Iterator` 상태가 호출하는 Lambda 함수의 역할을 코드로 보면 이렇습니다. 문서가 기술하는 입력·출력 계약(`count`·`index`·`step`을 받아 `index`를 올리고 `continue`를 반환)만 표현한 것입니다.

```javascript
// Iterator 상태가 호출하는 Lambda 핸들러.
// 입력으로 count(총 횟수) · index(현재 위치) · step(증가폭)을 받는다.
exports.handler = async function (event) {
  let index = event.index;
  const step = event.step;
  const count = event.count;

  // 인덱스를 단계만큼 증가시킨다
  index = index + step;

  return {
    index,
    step,
    count,
    // 인덱스가 개수보다 작으면 계속 반복한다는 뜻으로 true 를 반환한다
    continue: index < count,
  };
};
```

### 7.8 오류 처리: Retry 와 Catch 🆕

[8.3절](#83-예제-dynamodb-getitem-에서-lambda-invoke-로)의 정의에 `Retry`와 `Catch`가 등장하지만, 예제로만 보이고 필드의 기본값이나 제약은 잘 드러나지 않습니다.

| 기본 동작 | 내용 |
|---|---|
| 어디서 오류가 나는가 | **`Pass`와 `Wait`을 제외한 모든 상태**가 런타임 오류를 만날 수 있습니다 |
| 기본 처리 | 상태가 오류를 보고하면 Step Functions는 기본적으로 **상태 머신 실행 전체를 실패**시킵니다 |
| `Catcher`를 쓸 수 있는 상태 | `Task`, `Parallel`, `Map`. **최상위 상태 머신 실행 실패에는 쓸 수 없습니다** |
| 오류 이름 | **대소문자를 구분하는 문자열**이며, ASL이 정의한 내장 오류는 모두 **`States.`** 접두사로 시작합니다 |

#### `States.ALL`의 제약

`States.ALL`은 알려진 모든 오류 이름과 일치하는 와일드카드이지만 세 가지 제약이 있습니다.

| 제약 |
|---|
| `Catcher`에 **단독으로** 나타나야 합니다 |
| `States.DataLimitExceeded` **종단 오류를 잡을 수 없습니다** |
| `States.Runtime` **오류를 잡을 수 없습니다** |

그 밖의 내장 오류는 다음과 같습니다.

| 내장 오류 |
|---|
| `States.DataLimitExceeded` · `States.ExceedToleratedFailureThreshold` · `States.HeartbeatTimeout` · `States.Http.Socket` · `States.ItemReaderFailed` · `States.Permissions` · `States.ResultWriterFailed` · `States.Runtime` · `States.TaskFailed` · `States.Timeout` |

#### `Retry` 필드의 기본값

`Task`, `Parallel`, `Map` 상태는 retrier 객체 배열인 `Retry` 필드를 가질 수 있습니다.

| 필드 | 필수 | 기본값 | 범위 |
|---|---|---|---|
| `ErrorEquals` | **필수** | — | 잡을 오류 이름 배열 |
| `IntervalSeconds` | 선택 | **1** | 최대 99,999,999 |
| `MaxAttempts` | 선택 | **3** | 최대 99,999,999. **0은 재시도 안 함** |
| `BackoffRate` | 선택 | **2.0** | — |
| `MaxDelaySeconds` | 선택 | — | 0 초과 31622401 미만 |
| `JitterStrategy` | 선택 | — | — |

문서는 **프로덕션 코드가 `Lambda.ServiceException`과 `Lambda.SdkClientException` 같은 Lambda 서비스 예외를 처리해야 한다**고 명시합니다. [8.3절](#83-예제-dynamodb-getitem-에서-lambda-invoke-로)의 `Retry` 문이 바로 그 형태입니다.

재시도는 무료가 아닙니다. Standard 워크플로에서 **각 재시도가 추가 상태 전환으로 과금**됩니다([6.6절](#66-요금-모델)).

> — 출처: [Handling errors in Step Functions workflows](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)

## 8. 서비스 통합

### 8.1 세 가지 통합 패턴 🆕

세 가지 통합 패턴은 설명은 흔하지만 **공식 이름과 ASL 표기가 함께 제시되지 않는** 경우가 많습니다. 실습에서 리소스 URI에 접미사를 붙이는 순간 이 이름을 알아야 합니다.

| 패턴 공식 이름 | 설명 | ASL 리소스 URI 표기 | Standard | Express |
|---|---|---|---|---|
| **Request Response**(기본) | 서비스를 호출하고 HTTP 응답을 받자마자 다음 상태로 넘어갈 수 있도록 허용합니다 | 접미사 **없음** | 지원 | 지원 |
| **Run a Job** | 서비스를 호출하고 작업이 완료될 때까지 기다립니다 | **`.sync`** | 지원 | **미지원** |
| **Wait for a Callback with Task Token** | 태스크 토큰으로 서비스를 호출하고 해당 토큰이 페이로드와 함께 반환될 때까지 기다립니다 | **`.waitForTaskToken`** | 지원 | **미지원** |

각 패턴은 태스크 정의의 **`Resource` 필드 URI**로 제어합니다. 콜백 패턴은 `SendTaskSuccess` 또는 `SendTaskFailure` 호출로 재개하며, **실행이 1년 서비스 할당량에 도달할 때까지 대기**할 수 있습니다. 태스크 토큰은 **같은 AWS 계정의 프린시펄**이 전달해야 합니다.

#### `Resource` 값의 ARN을 오해하지 않기

ASL의 `Resource` 값은 ARN 형식을 따르는 고유 이름이지만 **실제 계정 리소스를 가리키지 않는 경우가 많습니다.**

| 부분 | 의미 |
|---|---|
| `arn:aws:states:` | Step Functions 통합용 **네임스페이스** |
| `:::` | 리전·계정 필드가 **비어 있음**을 뜻합니다. 워크플로가 실행되는 리전·계정에서 추론합니다 |
| 예외 | **Lambda로의 레거시 통합만** `Resource` 값이 실제 Lambda 함수 리소스를 지정합니다([7.7절](#77-예제-lambda-로-루프-반복하기)의 예제가 그 형태입니다) |

> — 출처: [Discover service integration patterns in Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/connect-to-resource.html)

### 8.2 최적화 통합과 AWS SDK 통합 🆕

통합 대상을 아홉 개 서비스(AWS Lambda, AWS Batch, AWS Fargate, Amazon ECS, Amazon DynamoDB, Amazon SNS, Amazon SQS, AWS Glue, Amazon SageMaker)와 "그 외 다수"로만 보기 쉽습니다. 현재는 통합 유형이 **두 가지로 구분**됩니다.

| 항목 | 최적화 통합(Optimized integrations) | AWS SDK 통합 |
|---|---|---|
| 무엇인가 | 특정 서비스를 상태 머신에서 쓰기 위한 **사용자 지정 옵션**을 제공합니다 | 상태 머신에서 **거의 모든 AWS 서비스 API 작업**을 직접 호출합니다 |
| 규모 | 통합 표에 **21개 서비스**가 나열됩니다(API Gateway, Athena, AWS Batch, Bedrock, Bedrock AgentCore 등) | **수천 개의 API 작업**에 접근할 수 있고, 표에는 "Over two hundred services"(**200개 이상 서비스**)로 기재되어 있습니다 |
| `Resource` 구문 | 서비스별 URI(예: `arn:aws:states:::dynamodb:getItem`) | `arn:aws:states:::aws-sdk:serviceName:apiAction.[serviceIntegrationPattern]` |
| 예 | `arn:aws:states:::lambda:invoke` | `arn:aws:states:::aws-sdk:ec2:describeInstances` |
| 파라미터 표기 | 서비스별 | 원 서비스 API가 camelCase여도 Step Functions에서는 **PascalCase**로 표기합니다 |
| 오류 이름 | 서비스별 | **`ServiceName.ErrorName`** 형식. 서비스가 `Exception` 접미사를 쓰지 않아도 Step Functions에서는 항상 붙여 참조합니다(예: `S3.BucketAlreadyExistsException`) |
| IAM 정책 | 자동 생성됩니다 | **자동 생성되지 않습니다.** 상태 머신 생성 후 역할 정책을 직접 구성해야 합니다 |

마지막 줄이 실습에서 가장 자주 막히는 지점입니다. AWS SDK 통합을 쓰면 상태 머신은 만들어지지만 실행이 권한 오류로 실패합니다.

```json
{
  "Comment": "AWS SDK 통합 예. EC2 DescribeInstances 를 직접 호출한다",
  "StartAt": "DescribeInstances",
  "States": {
    "DescribeInstances": {
      "Type": "Task",
      "Resource": "arn:aws:states:::aws-sdk:ec2:describeInstances",
      "Parameters": {},
      "End": true
    }
  }
}
```

> — 출처: [Learning to use AWS service SDK integrations](https://docs.aws.amazon.com/step-functions/latest/dg/supported-services-awssdk.html)

### 8.3 예제: DynamoDB GetItem 에서 Lambda Invoke 로 🔄

두 번째 ASL 정의입니다. 일부 원본 자료에는 이 예제에 여러 문제가 겹쳐 있어 정리가 필요합니다.

| 원본의 문제 | 이 문서의 처리 |
|---|---|
| 제목이 반복 패턴 예제와 같은 "예: Lamda를 사용한 루프 반복"인데 내용은 루프 반복이 아니라 DynamoDB `GetItem` → Lambda `invoke` **순차 워크플로**입니다. 제목이 반복 패턴 예제에서 복사된 것으로 보입니다 | 내용에 맞는 제목으로 고쳤습니다 |
| `Comment` 값이 `"Example of the Amazon States Language using a Pass state"`인데 이 정의에는 **`Pass` 상태가 없습니다** | `Comment`를 내용에 맞게 고쳤습니다 |
| 상태 이름을 `DynamoDBGetItem`(공백 없음)으로 적은 자료가 있지만 코드의 상태 이름은 `DynamoDB GetItem`(공백 있음)입니다 | **코드 기준**으로 통일했습니다 |
| 파라미터 이름을 `tableName`(소문자 t)으로 적은 자료가 있지만 코드는 `TableName`입니다 | **코드 기준**으로 통일했습니다 |
| `Catch`의 `Next` 대상이 `"Fail"`인데 텍스트가 잘려 그 상태가 정의되어 있는지 확인할 수 없습니다 | `Fail` 상태를 정의에 **포함**했습니다 |
| `FunctionName` ARN에 실제 계정처럼 보이는 12자리 숫자가 들어 있습니다 | 예시용 값 `123456789012`로 바꿨습니다 |
| 반복 패턴 예제의 제목도 "Lamda"로 오타입니다 | — |

원본은 `MaxAttempts` 뒤에서 잘려 있습니다. 아래 정의는 `BackoffRate`를 문서가 명시한 기본값 **2.0**으로 채운 것입니다([7.8절](#78-오류-처리-retry-와-catch)).

```json
{
  "Comment": "DynamoDB GetItem to Lambda Invoke sequential workflow",
  "StartAt": "DynamoDB GetItem",
  "States": {
    "DynamoDB GetItem": {
      "Type": "Task",
      "Resource": "arn:aws:states:::dynamodb:getItem",
      "Parameters": {
        "TableName": "NoteInventory",
        "Key": { "NoteName": { "S.$": "$.note" } }
      },
      "ResultPath": "$.DynamoDB",
      "Catch": [
        {
          "ErrorEquals": ["States.ALL"],
          "Next": "Fail"
        }
      ],
      "Next": "Lambda Invoke"
    },
    "Lambda Invoke": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "OutputPath": "$.Payload",
      "Parameters": {
        "Payload.$": "$",
        "FunctionName": "arn:aws:lambda:us-east-2:123456789012:function:ProcessDynamoDBRecords2:$LATEST"
      },
      "Retry": [
        {
          "ErrorEquals": [
            "Lambda.ServiceException",
            "Lambda.AWSLambdaException",
            "Lambda.SdkClientException"
          ],
          "IntervalSeconds": 2,
          "MaxAttempts": 6,
          "BackoffRate": 2
        }
      ],
      "End": true
    },
    "Fail": {
      "Type": "Fail"
    }
  }
}
```

이 정의의 동작을 풀어 설명하면 이렇습니다.

> 상태 머신은 DynamoDBGetItem 상태에서 시작합니다. (…) 이 태스크는 Amazon 리소스 이름(ARN)을 사용하는 리소스에서 수행합니다. tableName: NoteInventory 파라미터와 키 파라미터는 '$' 표기법을 사용하여 해당 입력에서 값을 끌어옵니다. ResultPath는 항목의 검색한 값을 사용하여 업데이트됩니다. 오류가 발생하면 오류를 포착한 다음 흐름을 실패 상태로 전송합니다. 성공한다면 흐름은 Lambda Invoke 상태로 계속 진행됩니다.
> Lambda Invoke 상태에서는 재시도 문에 주목해야 합니다.

문서로 확인한 결과, `Retry` 문(`Lambda.ServiceException`·`Lambda.AWSLambdaException`·`Lambda.SdkClientException`, `IntervalSeconds` 2, `MaxAttempts` 6)과 `Catch` 문(`ErrorEquals: States.ALL`)은 **실제 필드 구조와 일치**합니다. 잘 고른 예제라는 뜻입니다.

> — 출처: [Handling errors in Step Functions workflows](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-error-handling.html)

### 8.4 Lambda 최적화 통합 🆕

위 예제에서 `OutputPath`가 `$.Payload`인 이유를 알면 이 통합을 이해한 것입니다.

| 항목 | 내용 |
|---|---|
| 최적화 API | **`Invoke`** |
| 핵심 특징 1 | 응답의 **`Payload` 필드가 이스케이프된 JSON에서 JSON으로 파싱**됩니다 |
| 핵심 특징 2 | Lambda 함수 안에서 **예외가 발생하면 Task가 실패**합니다 |
| 태스크 결과 형태 | 함수 출력이 메타데이터 딕셔너리 안에 **중첩**되어 `ExecutedVersion`, `Payload`, `SdkHttpMetadata`, `SdkResponseMetadata`, `StatusCode`를 포함합니다 |
| 그래서 | 함수 출력만 다음 상태로 넘기려면 `OutputPath`로 **`$.Payload`** 를 뽑습니다 |
| 콜백 패턴 | `.waitForTaskToken`을 붙이면 콜백 패턴을 구현하고 이때 **`TaskToken`을 페이로드에 넣습니다** |
| 비동기 호출 | `InvocationType` 파라미터로 비동기 호출도 가능하며, 비동기 호출에서는 **하트비트 시간 초과가 즉시 시작**됩니다 |

`Resource` 필드에 함수 ARN을 직접 지정하는 **대안**도 있습니다([7.7절](#77-예제-lambda-로-루프-반복하기)의 형태). 이 경우 차이가 둘 있습니다.

| 대안(함수 ARN 직접 지정) | 내용 |
|---|---|
| 제약 | **`.waitForTaskToken`을 쓸 수 없습니다** |
| 결과 | 태스크 결과에 **함수 출력만** 담깁니다(메타데이터 중첩 없음) |

`Qualifier` 파라미터를 쓰거나 `FunctionName`에 버전·별칭을 지정하면 **IAM 정책 리소스 ARN에도 한정자를 포함**해야 합니다. 모든 버전·별칭을 허용하려면 `:*`를 씁니다.

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "lambda:InvokeFunction",
      "Resource": "arn:aws:lambda:us-east-2:123456789012:function:ProcessDynamoDBRecords2:*"
    }
  ]
}
```

> — 출처: [Invoke an AWS Lambda function with Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/connect-lambda.html)

### 8.5 활동 작업자 🆕

태스크 상태가 호출할 수 있는 대상에는 "활동 작업자"도 있습니다. 이것이 **Activities**입니다. 상태 머신의 태스크를 **Step Functions 외부에서 실행되는 작업자**가 수행하게 하는 방법입니다.

| 항목 | 내용 |
|---|---|
| 작업자가 될 수 있는 것 | EC2 인스턴스, Amazon ECS, 모바일 디바이스 등 **HTTP 연결을 만들 수 있는 어떤 애플리케이션**이든 됩니다 |
| 만드는 방법 | 콘솔 또는 **`CreateActivity`** 호출로 활동을 만들면 태스크 상태에 쓸 ARN이 제공됩니다 |
| 동작 | Step Functions가 활동 태스크 상태에 도달하면 워크플로는 **활동 작업자가 태스크를 폴링할 때까지 기다립니다** |
| 폴링 | 활동 작업자가 **`GetActivityTask`** 로 폴링하고 응답으로 `input`과 `taskToken`을 받습니다 |
| 보고 | 작업을 마치면 **`SendTaskSuccess`** 또는 **`SendTaskFailure`** 로 결과를 보고합니다 |
| 관련 API | `CreateActivity`, `GetActivityTask`, `ListActivities`, `SendTaskFailure`, `SendTaskHeartbeat`, `SendTaskSuccess` |
| 버전 관리 | 활동은 **버전이 없고 하위 호환이 기대**되므로, 하위 호환되지 않는 변경이 필요하면 **고유한 이름으로 새 활동**을 만듭니다 |
| 장기 실행 | `TimeoutSeconds`를 길게 설정하고 `SendTaskHeartbeat`를 주기적으로 보내면 활동이 **최대 1년까지** 실행 완료를 기다릴 수 있습니다 |
| 시간 초과 | 태스크가 시간 초과되면 Step Functions가 태스크 토큰을 무효화하고, 만료된 토큰을 쓰는 API 호출은 **`TaskTimedOut`** 예외로 실패합니다 |

제약을 하나 기억하세요. **활동은 Standard 워크플로에서만 지원됩니다**([6.4절](#64-워크플로-유형-standard-와-express)).

> — 출처: [Learn about Activities in Step Functions](https://docs.aws.amazon.com/step-functions/latest/dg/concepts-activities.html)

### 8.6 HTTP Task 🆕

통합 대상을 AWS 서비스로만 보면 **AWS 외부의 HTTPS 엔드포인트를 호출하는 방법**이 빠집니다. 그것이 HTTP Task입니다.

| 항목 | 내용 |
|---|---|
| 무엇인가 | 워크플로에서 **HTTPS API를 호출하는 `Task` 상태의 한 종류**입니다 |
| 호출 대상 | Stripe·Salesforce 같은 서드 파티 SaaS 애플리케이션의 **퍼블릭 API**와 Amazon VPC 안의 **HTTPS 기반 프라이빗 API** |
| 인증·연결 | **EventBridge connection**이 필요합니다. connection은 **Basic·OAuth·API Key** 인증 체계를 지원합니다 |
| 시크릿 | EventBridge가 **AWS Secrets Manager에 암호화된 시크릿**을 만들어 인증 파라미터를 저장하므로 상태 머신 정의에 시크릿을 하드코딩하지 않아도 됩니다 |
| `Resource` | **`arn:aws:states:::http:invoke`** |
| 필수 파라미터 | **`ApiEndpoint`**, **`Method`**, 그리고 `Authentication` 또는 `InvocationConfig`로 connection ARN |
| 선택 파라미터 | `Headers`, `QueryParameters` |
| 시간 초과 | 요청은 **60초 후 시간 초과**되며 이는 **하드 할당량**입니다. 시간 초과 시 **`States.Http.Socket`** 오류가 발생합니다 |
| 미지원 | **mTLS(상호 TLS)를 지원하지 않습니다** |
| 처리량 제한 | 버킷 크기 **300**, 초당 리필 **300** 의 토큰 버킷으로 제한됩니다 |
| IAM | Workflow Studio로 HTTP Task를 포함한 상태 머신을 만들면 HTTP Task용 IAM 정책이 포함된 실행 역할이 **자동 생성**됩니다 |

```json
{
  "Comment": "HTTP Task 예. 외부 HTTPS API 를 호출한다",
  "StartAt": "Call third party API",
  "States": {
    "Call third party API": {
      "Type": "Task",
      "Resource": "arn:aws:states:::http:invoke",
      "Parameters": {
        "ApiEndpoint": "https://api.example.com/v1/notes",
        "Method": "POST",
        "Authentication": {
          "ConnectionArn": "arn:aws:events:us-east-1:123456789012:connection/example-connection/00000000-0000-0000-0000-000000000000"
        },
        "Headers": {
          "Content-Type": "application/json"
        }
      },
      "End": true
    }
  }
}
```

> — 출처: [Call HTTPS APIs in Step Functions workflows](https://docs.aws.amazon.com/step-functions/latest/dg/call-https-apis.html)

상태 머신 전체를 실행하지 않고 상태 하나만 확인하는 방법이 있습니다.

| 방법 | 내용 |
|---|---|
| 콘솔의 **Test State** | 상태 정의와 입력을 제공하면 Step Functions가 그 상태를 실행하고 출력을 보여 줍니다. **상태 머신을 만들지 않아도 됩니다** |
| **`TestState`** API | 개별 상태를 테스트합니다. `inspectionLevel`은 **`INFO`(기본) · `DEBUG` · `TRACE`** 입니다. `TRACE`는 **HTTP Task에만** 제공되며 원시 HTTP 요청·응답을 보여 줍니다 |

#### 지원되지 않는 두 도구

로컬 테스트 방법을 찾다 보면 가장 먼저 마주치는 두 도구가 현재 문서에서 **unsupported로 명시**되어 있습니다. 알아 둘 필요가 있습니다.

| 도구 | 상태 | 내용 |
|---|---|---|
| **데이터 흐름 시뮬레이터**(Data flow simulator) | 지원되지 않음 | JSONPath 구문을 테스트하기 위해 만든 콘솔 도구입니다 |
| **AWS Step Functions Local** | 지원되지 않음 | 다운로드 가능한 버전입니다. **기능 동등성을 제공하지 않으며** 최적화 서비스 통합, 크로스 계정 액세스, 분산 맵을 지원하지 않습니다 |

문서는 Step Functions Local 대신 **`TestState` API로 배포 전에 상태 머신 로직을 단위 테스트**하도록 안내합니다.

### 9.3 버전과 별칭 🆕

상태 머신의 버전·별칭은 모듈 9의 Lambda 버전·별칭, 모듈 10의 API Gateway 스테이지에 대응하는 **Step Functions 쪽 배포 단위**여서 강의 흐름상 비어 있기 쉬운 지점입니다.

| 항목 | 내용 |
|---|---|
| 버전이란 | 상태 머신의 **번호가 붙은 불변 스냅샷**입니다 |
| 게시 방법 | 상태 머신에 대한 **가장 최근 개정(revision)** 에서 버전을 게시합니다 |
| ARN 형식 | 상태 머신 ARN + 버전 번호를 콜론으로 이은 형식(`arn:partition:states:region:account-id:stateMachine:myStateMachine:1`) |
| 실행 | 버전을 게시한 뒤에는 **버전 ARN으로 `StartExecution`** 을 호출할 수 있습니다 |
| 편집 | 버전은 **편집할 수 없습니다.** 상태 머신을 업데이트해 새 버전을 게시합니다 |
| 번호 | 1부터 시작해 **단조 증가**하며 **재사용되지 않습니다**(버전 10을 삭제한 뒤 새로 게시하면 11이 됩니다) |
| 버전 간 공통 | 모든 버전은 **같은 유형**(Standard 또는 Express)을 공유하고 이름·생성 날짜는 버전 간에 바꿀 수 없습니다. 태그는 상태 머신 **전역**에 적용됩니다 |
| 버전마다 다를 수 있는 것 | 상태 머신 **정의**, **IAM 역할**, **추적 구성**, **로깅 구성** |
| 한도 | 상태 머신당 최대 **1,000개** 버전(소프트 한도) |

### 9.4 실패한 실행 다시 시작하기: redrive 🆕

앞서 "실패한 태스크 Retry"와 "장애·재시도 관리"를 강조했습니다. `Retry`는 **상태 단위** 복구입니다. **실행 단위** 복구 수단인 redrive는 별도로 알아야 합니다.

| 항목 | 내용 |
|---|---|
| 무엇인가 | 최근 **14일** 안에 성공적으로 완료되지 않은 **Standard** 워크플로 실행(실패·중단·시간 초과)을 다시 시작합니다 |
| 어디서 이어지나 | **실패한 단계부터 같은 입력으로** 실행을 이어갑니다. 성공한 단계의 결과와 실행 이력은 **보존되어 다시 실행되지 않습니다** |
| 정의·ARN | 원래 시도와 **같은 상태 머신 정의와 실행 ARN**을 씁니다. 상태 머신 정의를 업데이트했다면 **새 실행을 시작해야** 합니다 |
| 과금 | redrive는 **상태 전환으로 계산되어** 과금에 영향을 줍니다([6.6절](#66-요금-모델)) |
| 재시도 횟수 | `Task`·`Parallel`·Inline `Map` 상태에 정의한 재시도 횟수는 redrive 시 **0으로 초기화**되어 최대 시도 횟수를 다시 쓸 수 있습니다 |
| Express | **지원하지 않습니다** |

자격 조건은 다음을 모두 만족해야 합니다.

| redrive 자격 조건 |
|---|
| **2023년 11월 15일 이후** 시작한 실행 |
| 상태가 `SUCCEEDED`가 **아님** |
| redrive 가능 기간 **14일**을 초과하지 않음 |
| 최대 열린 시간 **1년**을 초과하지 않음 |
| 실행 이벤트 이력 수가 **24,999 미만** |

> — 출처: [Restarting state machine executions with redrive](https://docs.aws.amazon.com/step-functions/latest/dg/redrive-executions.html)

## 10. 교재 대비 변경 사항

수강생이 공식 교재를 함께 볼 수 있으므로, 이 자료가 교재와 어디서 갈라지는지 한곳에 모았습니다. 앞 장에서 신규·교정으로 표시한 항목의 근거가 여기 있습니다.

### 10.1 교재와 다른 점

앞의 네 항목은 외부 문서로 확인한 것이고, 뒤의 네 항목은 **원본 자료 안에서 서로 어긋나는 내부 불일치**여서 외부 문서로 검증할 대상이 아닙니다. 후자에는 근거 칸에 `—`를 두었습니다.

| 항목 | 교재의 서술 | 확인된 내용 | 근거 |
|---|---|---|---|
| 시각화 도구 이름 | 일부 원본 자료는 `State Function Workflow Studio`, 다른 곳에서는 `Workflow Studio`로 적음 | 공식 이름은 **Workflow Studio**입니다. Step Functions 콘솔에서 워크플로를 편집하는 시각적 도구이며 Design·Code·Config 세 모드를 제공합니다. 콘솔 외에 **AWS Infrastructure Composer**와 **VS Code용 AWS Toolkit**에서도 쓸 수 있습니다 | [Workflow Studio](https://docs.aws.amazon.com/step-functions/latest/dg/workflow-studio.html) |

### 10.2 동작·기본값이 변경된 항목

| 항목 | 교재의 서술 | 현재 | 근거 |
|---|---|---|---|
| 워크플로 유형 선택 | 교재는 Step Functions를 소개하고 정의·시각화·실행 흐름을 제시하지만 **워크플로 유형을 전혀 언급하지 않습니다** | 상태 머신을 만들 때 **Standard(기본값) 또는 Express를 반드시 선택**하고 생성 후에는 변경할 수 없습니다. Standard는 최대 1년·exactly-once·상태 전환 과금이고, Express는 최대 5분·at-least-once(비동기) 또는 at-most-once(동기)·실행 수와 지속 시간 과금입니다. Express는 `.sync`·`.waitForTaskToken` 패턴, Distributed Map, 활동, redrive를 지원하지 않습니다 | [Choosing workflow type](https://docs.aws.amazon.com/step-functions/latest/dg/choosing-workflow-type.html) |
| 데이터 전달·변환 방식 | 교재의 ASL 정의가 **JSONPath 기반 필드와 `$` 표기법으로만** 설명 | **JSONata**가 쿼리·변환 언어로 추가되었고 **새 상태 머신에는 JSONata를 권장**합니다. JSONata를 선택하면 다섯 개의 JSONPath 필드가 `Arguments`와 `Output` 두 필드로 줄고 JSON 키 이름에 `.$`를 쓰지 않습니다. 또 **변수(Variables)** 의 `Assign` 필드로 한 단계에서 저장한 데이터를 이후 어느 단계에서든 참조할 수 있습니다. 쿼리 언어를 지정하지 않은 상태 머신은 하위 호환을 위해 JSONPath로 기본 설정되므로 **교재 예제는 지금도 동작합니다** | [Transforming data with JSONata](https://docs.aws.amazon.com/step-functions/latest/dg/transforming-data.html) |
| 통합 대상의 범위 | 교재는 9개 서비스와 "그 외 다수"로 제시 | 통합 유형이 두 가지로 구분됩니다. **최적화 통합**은 특정 서비스용 사용자 지정 옵션을 제공하며 표에 21개 서비스가 나열되고, **AWS SDK 통합**은 200개 이상 서비스의 API 작업을 `arn:aws:states:::aws-sdk:서비스:API` 형식으로 직접 호출합니다. 또 `arn:aws:states:::http:invoke`를 쓰는 **HTTP Task**로 AWS 외부 HTTPS API도 호출할 수 있습니다 | [AWS SDK service integrations](https://docs.aws.amazon.com/step-functions/latest/dg/supported-services-awssdk.html) |
| `Map` 상태의 처리 모드 | 교재는 "상태 입력에서 어레이의 여러 항목에 대해 동일한 단계를 실행합니다"로만 설명해 **처리 모드를 구분하지 않습니다** | **Inline**(기본)은 JSON 배열만 입력으로 받고 최대 **40개** 동시 반복을 지원하며 반복 이력이 부모 실행 이력에 추가됩니다. **Distributed**는 각 반복을 자체 실행 이력을 가진 하위 워크플로 실행으로 돌려(지정하지 않으면 **10,000 병렬**) Amazon S3의 대규모 데이터 소스에서 입력을 읽을 수 있으며 **Standard 전용**입니다 | [Map state in Distributed mode](https://docs.aws.amazon.com/step-functions/latest/dg/state-map-distributed.html) |
| Amazon CloudWatch Events | 교재는 EventBridge 이름만 나열하고 **이전 이름을 다루지 않습니다** | Amazon EventBridge는 이전에 **Amazon CloudWatch Events**라고 불렸습니다. CloudWatch Events에서 만든 기본 이벤트 버스와 규칙이 EventBridge 콘솔에도 나타나고 **동일한 API를 쓰므로 기존 코드는 그대로 동작**합니다. 다만 EventBridge에 추가되는 새 기능(파트너 이벤트, 스키마 레지스트리, EventBridge Pipes 등)은 CloudWatch Events에 추가되지 않습니다 | [EventBridge is the evolution of CloudWatch Events](https://docs.aws.amazon.com/eventbridge/latest/userguide/eb-cwe-now-eb.html) |

### 10.3 비권장·지원 종료된 항목

| 항목 | 상태 | 대체 | 근거 |
|---|---|---|---|
| `Map` 상태의 `Iterator` 필드와 `Map` 안의 `Parameters` 필드 | **비권장**(deprecated). 기존 정의는 계속 동작하지만 문서가 바꾸도록 강력히 권장 | `Iterator` → **`ItemProcessor`**, `Map` 안의 `Parameters` → **`ItemSelector`**. 반복 패턴 예제의 `Iterator`는 Map 상태의 필드가 아니라 **Task 상태의 이름**이므로 이 사용 중단과 무관합니다 | [Map state in Inline mode](https://docs.aws.amazon.com/step-functions/latest/dg/state-map-inline.html) |
| **AWS Step Functions Local**과 데이터 흐름 시뮬레이터 | **지원되지 않음**(unsupported). Step Functions Local은 기능 동등성을 제공하지 않으며 최적화 서비스 통합·크로스 계정 액세스·분산 맵을 지원하지 않습니다 | 콘솔의 **Test State** 또는 **`TestState` API**로 개별 상태를 테스트합니다. VS Code용 AWS Toolkit의 Workflow Studio 안에서도 개별 상태를 테스트할 수 있습니다 | [Testing and debugging state machines](https://docs.aws.amazon.com/step-functions/latest/dg/test-and-debug.html) |

교재는 두 도구를 언급하지 않습니다. 로컬 테스트 방법을 찾는 수강생이 가장 먼저 마주치는 경로여서 남겨 둡니다.
